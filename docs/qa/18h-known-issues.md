## §10 — калибровка персонажей, мебели и интерактивных объектов (уже было закрыто в Wave 2, перепроверено и исправлено в этой волне)

`docs/art/18h-character-environment-scale-audit.md` уже покрывал весь
обязательный список объектов §10 из Wave 2. При заходе на §10 в этой волне
перепроверил фактическую точность утверждений (не доверяя прошлой записи
слепо) и нашёл реальную неточность:

- Строка «Диван» утверждала «эффективная посадка ниже кресла — ожидаемо для
  дивана» без измерения — это была оценка на глаз, а не факт из кода (что
  противоречит заявленному принципу документа). Измерил реальную посадку
  (`Hips` bone на последнем кадре `sit.glb`/`sofaSit.glb`, FK) для всех 5
  персонажей: посадка на диване СТАБИЛЬНО ВЫШЕ посадки на кресле (на
  0.03–0.07 м), не ниже. Исправлено в таблице.
- По пути нашёл и исправил реальный (хоть и пока безвредный) баг в уже
  закоммиченном `tools/art/ambientClipFurnitureAlignment.test.ts`: его
  `readFloats` не учитывал собственный `accessor.byteOffset` (только
  `bufferView.byteOffset`) — для `pullUp.glb` (единственный файл, который он
  сейчас парсит) это никогда не проявлялось, потому что там у каждого канала
  свой `bufferView`, но для `sit.glb`/`sofaSit.glb`/`walk.glb` (несколько
  аксессоров в одном `bufferView`, упаковка `glTF-Transform`) это давало
  абсурдные значения, которые я сначала принял за реальный баг персонажа
  business_man. После фикса — тот же тест (турник) по-прежнему 5/5 зелёный.
- Попутно перепроверил «все клипы in-place, root motion = 0»
  (`docs/art/animation-library.md`) на `walk.glb` для 2 персонажей —
  подтверждено измерением (X/Z дрейф Hips = 0.0000 м), не только
  продекларировано.
- Уточнил документацию: «стулья переговорной» — тот же `Chair.tsx`
  компонент, что и рабочие кресла (`MeetingRoom.tsx` использует его
  напрямую), отдельного объекта не существует — прежде не было явно указано.

Добавлен §10-чек-лист по всем обязательным объектам в конец audit-документа.
Новых permanent-тестов на seat-hip-height не добавлял: расхождений не
найдено (посадка согласована с нарисованной мебелью у всех 5 персонажей),
а Wave 2 уже осознанно решила не заводить `InteractionAnchorSet` для
seating (клип целиком отвечает за позу) — не переоткрывал это решение без
найденного дефекта.

## §9 — исправление изменения масштаба персонажей (уже было закрыто, теперь подтверждено живым тестом)

Структурная и asset-level часть §9 была сделана ещё в Wave 1/2 (см.
`docs/art/18h-character-environment-scale-audit.md`, раздел «Инварианты
масштаба персонажа») — сам P1-баг («модель растёт во время диалога») был
причинён SCALE-треками в Meshy-клипах, устранён `tools/art/stripScaleTracks.mjs`
и закрыт guard-тестом `tools/art/characterIdentity.test.ts`. При заходе на
§9 в этой волне я перепроверил утверждение аудита («ни один файл
`src/character/**` не пишет в `.scale`») и обнаружил, что оно было ТОЛЬКО
ручным `grep`-аудитом в markdown, без автоматической защиты от регресса —
любой будущий PR мог тихо добавить `.scale` где-то в дереве персонажа и
никто бы не заметил, кроме E2E/ручной проверки. Закрыл разрыв:

- `tools/art/characterScaleInvariant.test.ts` (новый) — статический
  парсинг исходников `src/character/**` (тот же подход, что уже
  используется в `characterIdentity.test.ts` для GLB-ассетов): падает при
  любой записи в `.scale` персонажа (кроме двух проверенных held-prop
  компенсаций — кружка/ракетка/телефон) и при любом JSX `scale=` на
  `<CharacterModel>`/`<group>`/`<primitive>`.

Не сделано: полноценный live r3f-mount регресс-тест (реально смонтировать
`CharacterModel` через `@react-three/test-renderer`, прогнать idle→talking→idle
и сверить `.scale` по кадрам) — `useGLTF` требует реальный `fetch` GLB-файла,
которого в vitest/jsdom нет (нет dev/preview-сервера); `Office.test.tsx` по
той же причине уже подменяет `CharacterComponent={() => null}}` вместо
монтирования настоящей модели. Решил не изобретать отдельный GLTF-мок ради
одного теста — statement-level guard + asset-level guard + живой E2E (visual,
человеком) остаются трёхуровневой защитой, как и было.

## §8 — Safe area диалогового UI (закрыто отдельным заходом)

Ранее в этой волне была реализована только статическая эвристика (Wave 1):
`.dialogue-panel--cinematic` всегда компактна и всегда внизу, независимо от
типа кадра и реального положения голов. Реализован настоящий механизм:

- `src/game/cinematics/dialogueSafeArea.ts` (новый, чистая математика, без
  DOM/three.js-рендера) — `projectHeadsForShot()` проецирует мировые точки
  через одноразовую `PerspectiveCamera`, настроенную как боевая
  (`fov=40, near=0.05, far=100`, см. `CutsceneCamera.tsx`), позиционированную
  на КАДР, который вот-вот начнёт проигрываться (не на текущую
  промежуточную камеру во время transition) — решение принимается «перед
  запуском shot», как того требует спека. `pickDialoguePanelSide()` сверяет
  экранные координаты голов с footprint панели (аналитический прямоугольник,
  подогнанный под `.dialogue-panel--cinematic` в `ui.css`, с комментарием,
  что он обязан следовать этому CSS) и решает `center`/`left`/`right`.
- `cinematicDirector.ts` — `applySafeArea()` вызывается на каждую реплику (и
  для группового, и для парного режима, и для самого первого/`aimSafeWideGroup`
  кадра), используя ТЕ ЖЕ входные параметры (`type`/`subjectId`/`opts`), что
  и реальный `playShot()`/`aimSafeWideGroup()` для этой реплики — не
  отдельная параллельная догадка. Результат пишется в
  `useCinematicStore().panelSide`; `end()` сбрасывает его в `center`.
- `DialoguePanel.tsx` — читает `panelSide` только пока `cinematic` активен
  (не для обычных cutscene-диалогов — там этот механизм не подключён, вне
  скоупа: cutscene используют отдельный `attachPerLineShots`, не
  `beginConversationCinematic`), добавляет `dialogue-panel--left`/`--right`.
- `ui.css` — `.dialogue-panel--cinematic.dialogue-panel--left/--right`
  сдвигают панель к краю (`6vw` от соответствующей стороны) вместо
  центрирования — специфичность выше базового правила, поэтому реально
  побеждает.
- HUD во время cinematic уже скрывался ДО этой волны (`useCinematicStore`
  флаг существовал с 18D §8) — отдельного вида работы не потребовалось,
  только подтверждено код-ревью.

Не реализовано: `focusTarget: 'object'` на камеру/framing не влияет (как и
раньше, документированное ограничение §7); выбор framing (переключение типа
кадра, а не только позиции панели) при конфликте — текущая реализация решает
конфликт только сдвигом ПАНЕЛИ, не сменой самого кадра (переключение framing
на лету добавило бы риск рассинхронизации с уже устоявшейся shot-грамматикой
`cinematicShots.ts`/`cinematicDirector.ts`, не было признаков, что сдвига
панели недостаточно на реальных откалиброванных позициях). Многорезолюционный
E2E (1366/1920/2560) по-прежнему не автоматизирован — см. открытое
ограничение #4 ниже, актуально и для §8.

## §7 — реакции слушателей по DialoguePerformanceCue (закрыто отдельным заходом)

Ранее (Wave 4) числилось открытой проблемой: был только обобщённый
group-gaze, без структурированных реакций по metadata реплики. Реализовано:

- `src/character/performance/dialoguePerformanceCue.ts` — типы
  `ListenerReaction` (все 11 из §7) и `DialoguePerformanceCue`, плюс
  `REACTION_EMOTION` (6 реакций переиспользуют готовые emotion-позы —
  neutral/focused/concerned/surprised/controlled-frustration/relieved —
  никаких новых raw morph names, только typed enum-to-enum).
- `performanceStore.ts` — `listenerReactions` + `gazePoints` (фиксированная
  точка взгляда, например «на доску», в дополнение к взгляду на персонажа).
- `useCharacterPerformance.ts` — nod обобщён (раньше только ambient-чат),
  добавлены small-head-shake (yaw-осцилляция) и thinking (статичный
  наклон+уведённый взгляд) процедурно, тем же способом, что дыхание/emotion.
- `cinematicDirector.ts` — `applyCue()` в group И pair режимах,
  `focusTarget: 'whiteboard'`/`'player'` переопределяет дефолтный
  «слушатели смотрят на говорящего».
- `sprintKickoff.ts` — реальные cues на каждой реплике планёрки, подобранные
  по содержанию (не случайно): открывающая реплика → фокус на доску;
  разработчик с задачей → confident/focused-listening, без задачи →
  neutral/thinking; предупреждение о перегрузке → concerned/concerned-listening;
  Илья без замечаний → relieved/relieved-reaction, с замечаниями →
  focused/concerned-listening; закрывающее «Погнали» → confident/nod.

**Найден и исправлен по пути реальный regression-риск при разработке**: первая
версия `applyCue` ОЧИЩАЛА эмоцию говорящего на любой реплике без cue — это
стёрло бы существующее «Соня остаётся concerned весь разговор»
(`postAuditInteraction.ts`, ни один существующий диалог ещё не использует
`cue`). Исправлено: `speakerEmotion` теперь только УСТАНАВЛИВАЕТ, никогда не
чистит сама по себе; `listenerReaction` (новая концепция, конфликтовать не с
чем) остаётся per-line сбрасываемым. Закреплено regression-тестом.

Не реализовано: cues в остальных диалоговых скриптах (8 story-decision сцен,
post-audit разговор) — механизм полностью готов и покрыт тестами, но
существующие скрипты пока играют без явных cue (ведут себя как раньше 18H,
ничего не сломано). Добавление — по одному `cue: {...}` объекту на реплику,
без дальнейшей инженерной работы.

## Найдено и исправлено в этой волне (не «issues» — фиксирую как факт процесса)

Полный `npm run test:e2e` прогонялся впервые за весь ход 18H именно в Wave 4.
Нашёл два реальных P1-бага, оба не были видны юнит-тестам (требовали живого
браузера):

**P1a — `.dialogue-panel--cinematic` обрезала кнопку «Далее» для длинных реплик.**
`max-height: 24vh` стоял на ВСЕЙ панели (`ui.css`), а не только на тексте;
для короткой реплики влезало, для длинной (`security-baseline-path`, первая
реплика Сони — два предложения) кнопка выталкивалась за `overflow:hidden`
границу и переставала быть кликабельной, хотя визуально/в DOM оставалась
на месте. Исправлено: max-height убран с панели, остался только на
`.dialogue-text` (уже был, со своим `overflow-y:auto`) — панель теперь
всегда ровно по контенту, текст сам скроллится при необходимости.

**P1b — `cinematic.ready` мог ждать в разы дольше номинальной длительности кадра.**
Под headless software-рендером `flyTo`/`camera-controls.setLookAt()`
сходился за измеренные ~8.25с вместо ~1.1с — реплика (§5: «no line before
camera settled») блокировалась на всё это время. Исправлено:
`READY_TIMEOUT_MS=3500` в `cinematicDirector.ts` — тот же принцип
«timeout только как защита от зависания», что уже применялся в
`GATHER_TIMEOUT_MS`/`ARRIVAL_TIMEOUT_MS` этой же фичи.

Оба фикса подтверждены живым E2E-прогоном (`story-baseline.spec.ts`:
180с timeout дважды воспроизведён → зелёный за ~60-70с после обоих фиксов).
Заодно упрощён сам E2E-спек: цикл повторных кликов по маркеру убран в пользу
одного клика + одного ожидания — маркер является позиционирующимся каждый
кадр `<Html>`-оверлеем, повторный force-click во время ходьбы был лишним
риском гонки, не нужным при работающем `approaching`-guard
(`Level1StoryDecisionController.tsx`).

## Что НЕ является багом (явные, проверенные архитектурные решения)

- Турник недостижим стоя для персонажей ростом ~1.50м (Соня/Алина) без
  подскока — реалистичное следствие реальных пропорций тела при фиксированной
  высоте перекладины, не дефект калибровки (`docs/art/18h-character-environment-scale-audit.md`).
- Пинг-понг без discrete ball physics — осознанное соответствие §14 «это не
  мини-игра и не спортивный симулятор».
- Ambient-планировщик тикает в фоновой (свёрнутой) вкладке — то же поведение
  у ВСЕХ NPC-таймеров с Feature 04/16, не новый регресс 18H.
