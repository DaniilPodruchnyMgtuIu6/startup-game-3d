# 18H — Known issues (факт 2026-07-27, дополнено 2026-07-28, 2026-07-29)

## Третий проход: видео ещё в трёх разных по духу сценариях (2026-07-29)

По запросу игрока разнообразить приём «мультик вместо безмолвной камеры» —
не повторяя один и тот же тип сцены. Все три ролика — окружение/реквизит,
без персонажей (см. `assets/source/prompts/story-clips-diverse-scenarios.md`
за полными промптами и job id):

1. **security-breach-unlocked-monitor** (тревожная) — заменяет статичный
   `playInsert` на разблокированном мониторе в `securityBreach.ts` сразу
   после того, как Соня уходит не заблокировав экран.
2. **server-gateway-outage** (техническая) — заменяет статичный `playInsert`
   на сломанной стойке, но ТОЛЬКО для инцидента `gateway-outage`
   (`serverIncidentScenes.ts`); `auth-account-incident` и
   `database-exposure-review` намеренно остались на прежней 3D-постановке,
   чтобы не повторять один приём во всех трёх однотипных сценах.
3. **mvp-release-launch** (победная) — заменяет финальный безмолвный
   `establishing`-пролёт камеры в `mvpReleaseScene.ts` после того, как
   реальные 3D-персонажи уже отыграли `celebrate`; CEO нигде не показан
   (канон).

Все три интегрированы через тот же `playVideoCutscene`-паттерн с булевым
фолбэком на исходный 3D-кадр при недоступности файла/кодека. Кадры сверены
покадрово (0.2/2.5/4.6 с) — стиль и освещение стабильны, соответствуют
Art Bible (тёплый день / холодная тревога с красным LED / тёплый триумф).

## Второй проход: диалоговый портрет, видео потери данных (2026-07-29)

1. **Портрет в диалоге — ещё раз**: прошлый фикс (фикс. размер 190×253,
   `align-self: flex-end`) убрал прыгающий кроп, но переборщил в другую
   сторону — маленькая картинка, не растянутая по левой стороне панели,
   с пустым пространством над ней у двухстрочных реплик (живой отзыв).
   Возвращено `align-self: stretch` (растягивается на всю высоту панели,
   как и было задумано), добавлен только `min-height: 260px` —
   этого достаточно, чтобы очень короткая реплика не давала
   переувеличенный кроп, и он НИКОГДА не обрежет кнопку (может только
   увеличивать панель, не уменьшать).
2. **«Утро без проекта» получило видео**: вместо непонятного безмолвного
   отъезда камеры (`playShot('dolly-out', ...)`) теперь играет
   сгенерированный ролик (тот же приём, что у intruder) — медленный
   докрут на монитор с перечёркнутой иконкой папки посреди пустого
   офиса на рассвете. Полный откат на старый `dolly-out`, если файл/кодек
   недоступны.
3. **Найден и исправлен реальный баг воспроизведения видео**: первая
   сгенерированная версия ролика потери данных долетала до
   `currentTime === duration` (полностью декодирована, `readyState 4`),
   но событие `ended` браузер так и не отправлял — известный класс
   проблем с метаданными контейнера MP4. Раньше сцену спасал только
   30-секундный watchdog — заметная пауза для игрока. Добавлен
   постоянный `onTimeUpdate`-фолбэк в `VideoCutsceneOverlay.tsx`
   (`duration - currentTime <= 0.15s` → завершить) — ловит этот класс
   багов почти мгновенно для ЛЮБОГО будущего клипа с той же проблемой,
   не только для этого. Сам ролик тоже перегенерирован (чистый дубль
   без этой особенности), но код-фикс — это постоянная защита, а не
   разовая правка ассета.

## Сюжетные видеоклипы («мультики», запрос игрока 2026-07-28)

Проникновение в офис теперь открывается сгенерированным видеоклипом
(Higgsfield: nano_banana кейфрейм → kling3_0_turbo image-to-video, 5 с,
720p, muted): вариант «Илья останавливает курьера у входа» (identity
Ильи сохранён по портрету) и «курьер дошёл до рабочего места и роняет
монитор». Канон Feature 10 соблюдён: кража данных не показана, только
физический беспорядок. Клип заменяет ПОДХОД нарушителя; разбор
последствий (диалог, списания, риски) остаётся детерминированной
3D-сценой.

Надёжность: клик = пропуск; watchdog 30 с; при недоступности файла или
кодека (headless-браузеры без H.264) `playVideoCutscene` возвращает
false и сцена играет ПРЕЖНЮЮ полную 3D-постановку — игра не зависит от
видеоассета (контракт закреплён юнит-тестами videoCutscene.test.ts).

Известное ограничение: в E2E-хромиуме клип не декодируется (нет H.264)
— E2E всегда проверяет fallback-ветку; ветка с клипом проверена вручную
покадровой выгрузкой через Edge (см. кадры в prompt-файле реестра).

## Пятый живой отзыв: подтягивания «шея пропадает», посадка, ночной проход красоты (2026-07-28)

1. **Подтягивания пересобраны одинарным ретаргетом**: старая цепочка была
   Meshy-источник → Mixamo-риги (18C-эпоха) → новые Meshy-риги — двойной
   перенос в экстремальной позе (руки над головой) ломал шею/спину.
   Исходник экшена (job 664fdf80) скачан заново и ретаргетнут НАПРЯМУЮ на
   пять текущих ригов (скелеты идентичны — перенос почти тождественный) +
   lift/normalize. В тест окна репов добавлен инвариант целостности торса
   в висе (голова ≥0.4м над тазом на обоих концах окна) — «пропавшая шея»
   больше не пройдёт.
2. **Посадка — визуальная калибровка вместо косточной**: нормализация bone-
   высоты не учитывает разную геометрию мешей (бёдра/юбки) — потому «только
   backend сидит нормально». Модель проста: родная глубина клипа + малый
   видимый подъём; значения выставлены из слов игрока (Кирилл «чуть выше» →
   0.065; девочкам умеренные 0.075–0.08; Илье базовые 0.05; диван — единый
   +0.06 всем, при родной глубине «все тонули»). Осталась ручная сверка
   игроком — числа легко крутятся в конфигах персонажей (seatLift).
3. **Ночной проход красоты**: стены получили тонкую штукатурку (512²,
   tiled, тонируется цветом — стены были крупнейшей плоской поверхностью
   кадра); все восемь сцен решений Level 1 размечены DialoguePerformanceCue
   (эмоция говорящего + реакция слушателя по СМЫСЛУ реплики: surprised на
   «копию не проверяли», controlled-frustration на «отложить», sad на
   «скрыть риск» и т.д.) — раньше сцены решений шли без эмоций вовсе.

## Четвёртый живой отзыв: плавность/«дёрганность», финальные штрихи (2026-07-28)

1. **«Дёрганная» походка всех персонажей — числовой корень**: единая
   глобальная скорость перемещения 1.4 м/с прокручивала walk-клипы быстрее
   их родного темпа (игрок ×1.31, Соня ×2.03 — ноги «строчили»). Теперь
   персонаж ПЕРЕМЕЩАЕТСЯ со скоростью родного темпа своего клипа
   (`walkSpeedFor`, кламп 0.8–1.45), а timeScale клипа ≈1 — спокойный
   естественный шаг, стопы приклеены. walkPace всех пяти обновлён на
   замеренные значения v2-клипов (устаревшие герои: 0.99→0.69, 1.68→1.15,
   1.77→1.38, 1.6→1.4).
2. **FPS без потери качества**: (а) `powerPreference: 'high-performance'` —
   на двух-GPU Windows-ноутбуках браузер без этого часто отдаёт страницу
   встроенной карте (самый большой реальный рычаг fps); (б) горячий путь
   движения переведён на мутацию на месте — раньше КАЖДЫЙ шаг КАЖДОГО
   идущего тела на КАЖДОМ кадре создавал новую иммутабельную копию словаря
   персонажей и будил все селекторы стора (аллокации + GC-рывки); ничего
   не читает позиции реактивно (проверено), арайвалы идут через
   state-transition нотификации.
3. **Качество вверх, не вниз**: тени PCFSoft + карта 2048 (было: жёсткие
   1024 — «грязные полосы» по полу, видны на walkshots), radius 4 —
   мягкое контактное затенение (живой кадр:
   docs/art/office/18h-soft-shadows-live.png).
4. **Откат диванных офсетов**: нормализация посадки к самому высокому ригу
   посадила Соню НА подлокотник (парила над подушками — видно на live-кадре).
   Диван вернулся к родной глубине каждого клипа (мягкая мебель — утопание
   уместно); офсеты кресел/стульев (реальный дефект «девочки проваливаются»)
   сохранены.
5. Походка игрока после спайн-фикса перепроверена живыми кадрами в зуме —
   прямой естественный шаг (walkshots2/w0-w2). Если у игрока «всё ещё
   сломано» — вероятен кэш браузера с досфиксовыми GLB: жёсткий refresh
   (Ctrl+F5) обязателен после обновления ассетов.

## Третий живой отзыв: «ходит скрепкой», «текстуры ужасные» (исправлено 2026-07-28)

1. **«Скрепка» — системный дефект ретаргета, задевал ВСЕ пять ригов.**
   Meshy именует позвоночник СВЕРХУ ВНИЗ (иерархия `Hips → Spine02 →
   Spine01 → Spine`, где `Spine` несёт плечи и шею — проверено по children
   каждого v2-рига), а маппинг `retargetMeshyClip` считал по-миксамовски
   (Spine — нижний): вращения верхнего и нижнего позвонков менялись местами
   в КАЖДОМ ретаргетнутом клипе. У четырёх героев зигзаг прятал скиннинг,
   у более длинного торса основателя — видимая «скрепка» (голова +0.26м над
   тазом вместо +0.6). Исправление: rig-aware канонизация имён (Mixamo —
   только срез префикса; Meshy — инвертированный spine-map), перегенерация
   всех клипов всех пяти ригов из бэкапов + повторный lift/normalize pullUp.
   После фикса дельта голова-таз: 0.47–0.61м у всех. Закреплено
   регресс-тестом осанки (walk/talk/type, оба конца клипа, все риги).
   Попутно: walkPace игрока перемерен после фикса (1.07).
2. **Ещё одна жертва того же нейминга**: поиск «груди» в performance-слое
   (`/Spine2$/`) не находил НИЧЕГО на v2-ригах (у Meshy грудь — голый
   `Spine`) — дыхание/наклоны груди были тихо мертвы со дня свапа моделей.
   `findBone` стал принимать упорядоченные кандидаты на оба нейминга.
3. **«Текстуры ужасные»**: два плоскоцветных материала доминируют в каждом
   кадре — `woodDesktop` (все столешницы) и `chairFabric` (все рабочие
   кресла). Сгенерированы и подключены реальные поверхности: дубовая
   фактура столешниц (1024²) и нейтральная ткань-сетка кресел (512²,
   почти серая — тонируется существующим цветом кресла через map*color,
   одна текстура на все цвета). Оба файла в бюджете 18A (≤200КБ).
   Живой кадр приёмки: docs/art/characters/player-founder/
   model-v2-posture-fixed.png (прямой игрок + фактуры мебели).

## Второй живой отзыв: «угробил качество», ходьба игрока, теннис, посадка (все исправлены 2026-07-28)

1. **Adaptive quality УДАЛЁН** — авто-даунгрейд ЗАПИСЫВАЛ пониженный tier в
   persist, и игра «навсегда» становилась некрасивой (низкий тир без теней/AO
   у игрока, который хотел красоту). Вместо него: видимый переключатель
   качества в игровом UI (`QualityMenu`, верхний правый угол, скрывается в
   киносценах), persist v1-миграция сбрасывает всем сохранённый tier обратно
   на `high`. Урок: автоматика не имеет права необратимо решать за игрока,
   как выглядит игра.
2. **Ходьба игрока**: после свапа модели walkPace остался от СТАРОГО клипа
   (1.33), а новый клип шагает 1.17 м/с — стопы скользили на ~14%.
   Методика подтверждена: у старой модели конфиг 1.33 ровно равен
   геометрическому замеру её клипа (2×макс. разлёт стоп / период = 1.325).
   Выставлено 1.17. ЗАМЕЧЕНО ПОПУТНО: у всех четырёх героев конфиги тоже
   стары (замеры их v2-клипов: Соня 0.69 vs конфиг 0.99, Алина 1.15 vs
   1.68, Кирилл 1.37 vs 1.77, Илья 1.40 vs 1.6) — их стопы тоже скользят,
   но правка удвоила бы частоту шагов Сони: требует визуальной приёмки,
   отложено с зафиксированными числами.
   Все клипы нового рига перепроверены: луповые замыкаются (hips gap
   ≤0.007м; исключение agree — 0.227м на 13-секундном цикле, редкий
   заметный «шов», унаследован от исходника, некритично), sit==sitIdle по
   контакту, walk без проседания стоп.
3. **«Один повёрнут от стола» — настоящий корень**: `arrive('perform')`
   ТЕРЯЛ target, а facing применяется из `state.target` — персонаж оставался
   повёрнутым по направлению последнего шага пути. Мои развороты триггеров
   были необходимы, но недостаточны. Исправлено переносом target в
   performing-состояние (+ regression-тест машины). Это чинит ВСЕ
   walk-then-perform активности: обе стороны тенниса, турник, взгляд в окно,
   whiteboard-glance.
4. **Теннис — настоящий розыгрыш**: общий фазовый модуль
   (`pingPongRhythm.ts`) для мяча и замахов от абсолютных часов — удар
   происходит ровно в момент прилёта мяча (юнит-тесты фаз); мяч летит в
   МИРОВЫХ координатах между фактическими игроками (какой бы стороной/
   поворотом ни стоял стол) с реальной формой полёта: дуга вниз → отскок о
   стол на половине принимающего → подскок к ракетке; замах = замах-коил
   корпуса (windup) + проводка (strike), между обменами — ready-стойка;
   головы следят за соперником (setGazePair на время матча).
5. **Посадка по росту** (§11): FK-замер таза всех пяти ригов на финальном
   кадре sit/sitIdle/sofaSit показал разброс 8–12см на одной мебели — Соня
   (самая низкая) проваливалась в сиденье до 10см, Илья парил. Введён
   пер-персонажный `seatLift` по семействам посадки (кресло/стул/диван),
   якорь — принятый вид business_man; поправка плавно набирается за время
   sit-клипа (старт клипа — стоя, мгновенный лифт парил бы ноги) и быстро
   сбрасывается при вставании. Значения и замеры — в конфигах персонажей.

1. **Клик по теннисному столу ничего не делал**: у side-триггеров не было

   (а) бар повёрнут `+π/2` фронтом В СТЕНУ (точка стойки в 0.4м СНАРУЖИ

3. **Вис вместо подтягиваний + руки не на перекладине**: клип заканчивал

## §4 — barrier готовности участников (перепроверен после §3-переписывания gather; API-адаптация зафиксирована)

Ядро барьера переписано в §3 (живое присутствие). Сверка восьми критериев
готовности §4 с фактическим кодом (`isParticipantReady` + `gatherParticipants`):

| Критерий §4 | Статус |
|---|---|
| существует | ✓ живое присутствие, спавн после старта gather подхватывается |
| не в другой blocking scene | адаптация: гарантируется уровнем вызова — kickoff стартует только при `canAutoAdvanceWorkday` (нет катсцены/миниигры/диалога/blocking overlay) + §9-гард «один cinematic». Сам барьер чужой `sceneOwned` не проверяет; ambient-claims снимаются `releaseClaims` — сюжет вытесняет ambient (§13-приоритет), это желаемое поведение |
| position tolerance | ✓ 0.55м |
| rotation tolerance | адаптация: поворот не ожидается, а детерминированно выставляется в `finish()` (`setTransform` с `facingY` слота) — нет ожидания и нет дрожания |
| locomotion завершена | ✓ READY_STATES не включает walking |
| animation state cinematic-ready | ✓ эквивалент — READY_STATES (idle/talking/performing/looking) |
| canonical scale сохранён | ✓ by construction: в characterStore нет поля scale, масштаб применяется один раз в корневом model-компоненте (§9) — дрейфовать нечему |

Timeout-политика §4: диагностика есть (`timedOut`-список + console.warn),
safe fallback — snap на слот, камера не целится в отсутствующих
(`presentGroup`), duplicate actor не создаётся (закреплено тестом «gather
never creates or duplicates an actor»), бесконечного зависания нет
(закреплено fake-timers-тестом таймаута).

slots уже несут characterId, а `sceneId` не нужен, пока §9 гарантирует один
активный cinematic.

## §5 — синхронизация камеры и реплик (перепроверено; найден и закрыт разрыв: игрок мог уйти из кадра)

Машина состояний кадра из §5 (`requested→validating→transitioning→settled→
speaking→reaction→completed`) реализована адаптацией: не enum, а awaited
promise-цепочка kickoff (`gather → ready → resettle → startDialogue →
per-line aims → end`) с bounded settle (`withReadyTimeout`). Требование
«реплика начинается только в settled» закреплено компонентным тестом
`WorkdayFlowController.test.tsx` (первая реплика после gather+settle,
маркер shown — прямо перед репликой).

«Персонаж не покидает slot во время реплики»: для NPC выполняется через
`sceneOwned` (автономный мозг на паузе, `useNpcBrain` его проверяет), но
ИГРОК — тоже участник сцены, а kickoff был ЕДИНСТВЕННЫМ блокирующим
разговором без `setInputLocked(true)` (postAudit, storyDecision,
SecuritySpecialist, FreeNpcChat — все лочат): клик в пол во время киносцены
уводил игрока из его слота. Исправлено: input лочится перед gather и
отпускается при закрытии диалога (та же store-подписка, что в остальных
разговорах) и в catch-ветке. «Далее» — DOM-кнопка, продвижение реплик
работает под локом. Закреплено компонентным тестом.

«Камера не догоняет NPC, вернувшегося в planner»: ✓ — `end()` снимает
tracking-interval ДО освобождения ownership, а до `end()` участники не
могут вернуться в planner.

## §6 — camera target validation и fallback (перепроверено; safe-wide теперь охватывает всех)

Сверка чек-листа §6 с фактическим кодом:

- «target не покинул cinematic ownership» ✓ — участники owned до `end()`
  (§5), игрок с этой волны под input lock.
- «face/head anchor валиден» ✓ — `eyePoint` тотален (высота от seated/
  standing), NaN-инварианты закреплены 18D-тестами.
- «projected bounding box в safe frame» — частично: проекция голов
  используется для выбора СТОРОНЫ панели (§8), не для рефрейминга кадра.
  Осознанная адаптация: рефрейминг заменён детерминированным выбором
  стороны/дистанции (pickSafeShotSide + clamp + fallback).
- «camera path не пересекает геометрию» — ИЗВЕСТНОЕ ОГРАНИЧЕНИЕ: blend
  между кадрами не трассируется по геометрии; митигация — endpoint'ы
  кадров всегда в комнате target'а, а pickSafeShotSide уводит их от стен
  (транзиентный «бежевый» кадр из §3-прогона был именно mid-blend у стены).
  Полная трассировка пути — кандидат на отдельную итерацию, если транзиенты
  останутся заметными на GPU (под SwiftShader blend растянут в десятки раз
  и не показателен).

Найденный и закрытый изъян: обязательный safe-wide-group-shot строился по
ПЕРВОМУ и ПОСЛЕДНЕМУ участникам списка (Соня↔Алина, ~1.3м) — камера
подъезжала на 2.4м, и участники середины прохода (игрок, Кирилл) нависали

кадр охватывает весь состав, а дистанция камеры растёт с шириной оси
(«показывать всех реально присутствующих участников»). Закреплено тестом
на реальной геометрии слотов.

## §3 — meeting slots (были в Wave 1; перепроверка нашла ДВА слота внутри мебели — исправлено)

Существующие тесты §3 проверяли уникальность, separation, границы комнаты и
required/optional-флаги, но требование «slots не находятся внутри мебели»
проверялось только по границам КОМНАТЫ — препятствия мебели регистрируются
при mount реальных компонентов (`useObstacle` берёт world bounds отрендеренных
мешей), и чистый unit-тест их никогда не видел.

Новый интеграционный тест `meetingSlotsWalkable.test.tsx` монтирует реальный
офис через `@react-three/test-renderer` (паттерн `Office.test.tsx`) и требует,
чтобы каждый слот был на реально проходимой клетке nav-сетки. Первый же прогон
нашёл два дефекта:

- `meeting-slot-kirill` (x+2.2/z-0.6 от доски) сидел внутри footprint+margin
  стола кластера `[-3,4]`;
- `meeting-slot-alina` (x+2.0/z+1.5) — внутри ВТОРОГО стола того же кластера
  (проявилось после исправления первого — тест падает на первом нарушении).

Симптом до исправления: gather каждый kickoff молча уводил обоих через
`nearestWalkable` рядом с их отметками (в пределах 0.55м tolerance, поэтому
без 9с-таймаута и без падений E2E — визуально персонажи стояли у кромки
стола, не на авторской отметке). Слоты перенесены: Кирилл — x+2.9/z-0.9
(глубже в проход), Алина — x+1.0/z+0.4 (пристенная проходимая полоса, север
доски — зеркально Соне, ведущей у южного края). Separation ≥0.9м сохранён
(валидатор зелёный), композиция полукруга к доске сохранена.

Адаптации типа слота относительно спеки (осознанные, без изменений):
`facing` — yaw-скаляр `facingY`, не vec3 (конвенция проекта);
`preferredShotSide` не заведён — режиссёр и так чередует стороны покадрово;
fallback-ступень «предопределённый fallback slot» покрыта
`nearestWalkable` + snap-с-диагностикой (обязательный участник никогда не
удаляется молча — timedOut-список + console.warn).

Попутно: в полном E2E-прогоне после переноса слотов один раз упал
`story-baseline.spec.ts` (marker-click → диалог не открылся). Спека вообще
не задействует kickoff/слоты (fresh free-play seed, спринт не активен) —
регрессия §3 исключена. Первая версия упрочнения («медленный retry:
3 клика × 20с») сама упала при перепроверке — покадровый разбор видео
Playwright показал НАСТОЯЩИЙ механизм из двух слоёв:

1. первый клик по маркеру СРАБОТАЛ, но под SwiftShader ходьба через офис +
   §2-settle камеры заняли >20с — waitFor попытки истёк прямо перед
   открытием диалога (на видео диалог открыт с ~95с и висит нетронутым);
2. повторный `marker.click` завис навсегда: при старте сцены
   `StorySceneMarker` размонтируется (`status !== 'available'` → null),
   а `actionTimeout` в playwright.config не задан (по умолчанию БЕЗ
   лимита) — click() бесконечно ждал появления элемента и съел весь
   180с-бюджет теста. `.catch()` не спасает: промис не резолвится.
   В отчёте это выглядело как «диалог не открылся» на строке финального
   expect — артефакт снятия теста по таймауту.

То есть retry путал два режима: «клик промахнулся» (маркер на месте —
кликнуть снова) и «клик сработал, диалог ещё едет» (маркер исчез — кликать
нельзя, только ждать). Финальное упрочнение: перед повторным кликом
проверяется `marker.isVisible()` (маркер исчез → пропустить клик и ждать
диалог), а сам клик ограничен `timeout: 2_000` — зависание невозможно
конструктивно. Пара story-baseline + workday, воспроизводившая падение,
после фикса зелёная (1.2м / 45с / 22с).

## §2 — единый жизненный цикл групповой сцены (был закрыт в Wave 1, при перепроверке найден и закрыт реальный timing-разрыв)

Пошаговая сверка kickoff-потока (`WorkdayFlowController.tsx`) со всеми 15
шагами lifecycle из §2 подтвердила порядок: ownership (`ownIds` →
`sceneOwned`, останавливает ambient-мозги) резервируется ДО gather; gather
освобождает старые claims (`releaseClaims`) и ведёт участников к слотам;
барьер ждёт готовых; finish() выравнивает позицию/поворот; камера awaited;
`end()` возвращает camera/planner/слоты. Синхронизация — promises и
store-подписки; все setTimeout — только documented failure-guards
(GATHER 9с / READY 3.5с / snap), что §2 явно разрешает.

**Найденный разрыв**: `cinematic.ready` покрывает только ОТКРЫВАЮЩИЙ переход
камеры, который прицеливается в момент `begin()` — пока актёры ещё идут к
слотам (это осознанно: игрок смотрит сбор команды, пустого кадра нет). Но
`ready` ограничен 3.5с, а gather — до 9с: к моменту завершения gather
`ready` давно resolved, и первая реплика могла открыться, пока камера ещё
доигрывает blend от последнего 450мс-tracking-перецеливания к финально
собравшейся группе — т.е. «камера завершила переход» из §2 выполнялось для
пред-gather композиции, не для собранной группы.

Исправление: `ConversationCinematicHandle.resettle()` — одно свежее
перецеливание текущего кадра по АКТУАЛЬНЫМ позам с awaited settle (bounded
тем же `withReadyTimeout`); kickoff вызывает его после gather перед первой
репликой. `currentAim` стал promise-returning (tracking-loop не изменился),
no-op guard-handle (§9) тоже несёт `resettle`. Закрыто 3 юнит-тестами.

Цена: +~1.1с реального времени до первой реплики kickoff (одно перецеливание
с blend) — это и есть требуемое «дождаться settle на собравшейся группе».

**КОРРЕКЦИЯ (найдена в §3 live-прогоне, исправлена)**: пошаговая сверка выше
была верна для кода цепочки await, но весь конвейер был мёртв в рантайме —
до этой правки НИ ОДИН kickoff не шёл киносценой. `beginConversationCinematic`
в конце `begin()` синхронно вызывает `applyCurrent()`; kickoff открывает
диалог только ПОСЛЕ gather, поэтому в этот момент `activeDialogue === null`
и ветка `autoEndOnDialogueClose` немедленно вызывала `end()` — handle
становился зомби (ownership снят, камера возвращена, `resettle()` мгновенно
резолвится через `ended`). Симптом на видео: планёрка на геймплейной
изометрии, HUD виден, панель полноразмерная. Тот же баг убивал кинематограф
интро Ильи (`SecuritySpecialistController.runTalk` тоже вызывает begin до
startDialogue). Парные сцены 17A/17B не страдали — там begin вызывается при
уже открытом диалоге, поэтому и story-baseline выглядел правильно.

Исправление: guard `dialogueSeen` — auto-end срабатывает только после того,
как диалог хотя бы раз был открыт («end when the dialogue CLOSES» требует,
чтобы он открылся). Юнит-тест: begin с autoEnd до открытия диалога
переживает `begin()` и посторонние обновления gameStore, но завершается на
реальном open→close.

Попутные находки того же live-прогона:

1. **Gather стартовал по пустому стору** (reload в день 1: kickoff-эффект
   срабатывает до маунта NPC-контроллеров) — снапшот `present` видел пустой
   офис, gather резолвился вакуумно, реплика шла по идущим через офис
   персонажам. Исправление: presence в `gatherParticipants` вычисляется
   живо на каждом изменении стора; обязательный участник, не заспавнившийся
   к timeout, попадает в `timedOut`-диагностику (§4), опоздавший спавн
   получает walk-order в момент появления. `participants` в
   WorkdayFlowController больше не фильтруется по стору (presence
   разрешается ниже по конвейеру; ненанятый Илья по-прежнему исключается
   через `presentGroup()`).
2. **Safe-wide-кадр смотрел в стену**: ось Соня↔Алина идёт почти вдоль
   стены с доской, перпендикуляр `side=1` нырял в стену — clamp ставил
   камеру в 0.45м от штукатурки (пустой бежевый кадр на видео). Исправление:
   `pickSafeShotSide` (cinematicSafety) выбирает сторону two-shot по
   максимальной camera-target дистанции после clamp (fallback = 0);
   для реальной геометрии слотов выбирается открытый пол (2.4м композиция),
   отвергнутая сторона уходит в raised-fallback. Юнит-тест на реальных
   KICKOFF_SLOTS.

## §8 — Safe area диалогового UI (закрыто отдельным заходом)

Ранее в этой волне была реализована только статическая эвристика (Wave 1):
`.dialogue-panel--cinematic` всегда компактна и всегда внизу, независимо от
типа кадра и реального положения голов. Реализован настоящий механизм:

- `src/game/cinematics/dialogueSafeArea.ts` (новый, чистая математика, без
  DOM/three.js-рендера) — `projectHeadsForShot()` проецирует мировые точки
  через одноразовую `PerspectiveCamera`, настроенную как боевая
  (`fov=40, near=0.05, far=100`, см. `CutsceneCamera.tsx`), позиционированную
  на КАДР, который вот-вот начнёт проигрываться (не на текущую
  промежуточную камеру во время transition) — решение принимается «перед
  запуском shot», как того требует спека. `pickDialoguePanelSide()` сверяет
  экранные координаты голов с footprint панели (аналитический прямоугольник,
  подогнанный под `.dialogue-panel--cinematic` в `ui.css`, с комментарием,
  что он обязан следовать этому CSS) и решает `center`/`left`/`right`.
- `cinematicDirector.ts` — `applySafeArea()` вызывается на каждую реплику (и
  для группового, и для парного режима, и для самого первого/`aimSafeWideGroup`
  кадра), используя ТЕ ЖЕ входные параметры (`type`/`subjectId`/`opts`), что
  и реальный `playShot()`/`aimSafeWideGroup()` для этой реплики — не
  отдельная параллельная догадка. Результат пишется в
  `useCinematicStore().panelSide`; `end()` сбрасывает его в `center`.
- `DialoguePanel.tsx` — читает `panelSide` только пока `cinematic` активен
  (не для обычных cutscene-диалогов — там этот механизм не подключён, вне
  скоупа: cutscene используют отдельный `attachPerLineShots`, не
  `beginConversationCinematic`), добавляет `dialogue-panel--left`/`--right`.
- `ui.css` — `.dialogue-panel--cinematic.dialogue-panel--left/--right`
  сдвигают панель к краю (`6vw` от соответствующей стороны) вместо
  центрирования — специфичность выше базового правила, поэтому реально
  побеждает.
- HUD во время cinematic уже скрывался ДО этой волны (`useCinematicStore`
  флаг существовал с 18D §8) — отдельного вида работы не потребовалось,
  только подтверждено код-ревью.

Не реализовано: `focusTarget: 'object'` на камеру/framing не влияет (как и
раньше, документированное ограничение §7); выбор framing (переключение типа
кадра, а не только позиции панели) при конфликте — текущая реализация решает
конфликт только сдвигом ПАНЕЛИ, не сменой самого кадра (переключение framing
на лету добавило бы риск рассинхронизации с уже устоявшейся shot-грамматикой
`cinematicShots.ts`/`cinematicDirector.ts`, не было признаков, что сдвига
панели недостаточно на реальных откалиброванных позициях). Многорезолюционный
E2E (1366/1920/2560) по-прежнему не автоматизирован — см. открытое
ограничение #4 ниже, актуально и для §8.

## §7 — реакции слушателей по DialoguePerformanceCue (закрыто отдельным заходом)

Ранее (Wave 4) числилось открытой проблемой: был только обобщённый
group-gaze, без структурированных реакций по metadata реплики. Реализовано:

- `src/character/performance/dialoguePerformanceCue.ts` — типы
  `ListenerReaction` (все 11 из §7) и `DialoguePerformanceCue`, плюс
  `REACTION_EMOTION` (6 реакций переиспользуют готовые emotion-позы —
  neutral/focused/concerned/surprised/controlled-frustration/relieved —
  никаких новых raw morph names, только typed enum-to-enum).
- `performanceStore.ts` — `listenerReactions` + `gazePoints` (фиксированная
  точка взгляда, например «на доску», в дополнение к взгляду на персонажа).
- `useCharacterPerformance.ts` — nod обобщён (раньше только ambient-чат),
  добавлены small-head-shake (yaw-осцилляция) и thinking (статичный
  наклон+уведённый взгляд) процедурно, тем же способом, что дыхание/emotion.
- `cinematicDirector.ts` — `applyCue()` в group И pair режимах,
  `focusTarget: 'whiteboard'`/`'player'` переопределяет дефолтный
  «слушатели смотрят на говорящего».
- `sprintKickoff.ts` — реальные cues на каждой реплике планёрки, подобранные
  по содержанию (не случайно): открывающая реплика → фокус на доску;
  разработчик с задачей → confident/focused-listening, без задачи →
  neutral/thinking; предупреждение о перегрузке → concerned/concerned-listening;
  Илья без замечаний → relieved/relieved-reaction, с замечаниями →
  focused/concerned-listening; закрывающее «Погнали» → confident/nod.

**Найден и исправлен по пути реальный regression-риск при разработке**: первая
версия `applyCue` ОЧИЩАЛА эмоцию говорящего на любой реплике без cue — это
стёрло бы существующее «Соня остаётся concerned весь разговор»
(`postAuditInteraction.ts`, ни один существующий диалог ещё не использует
`cue`). Исправлено: `speakerEmotion` теперь только УСТАНАВЛИВАЕТ, никогда не
чистит сама по себе; `listenerReaction` (новая концепция, конфликтовать не с
чем) остаётся per-line сбрасываемым. Закреплено regression-тестом.

Не реализовано: cues в остальных диалоговых скриптах (8 story-decision сцен,
post-audit разговор) — механизм полностью готов и покрыт тестами, но
существующие скрипты пока играют без явных cue (ведут себя как раньше 18H,
ничего не сломано). Добавление — по одному `cue: {...}` объекту на реплику,
без дальнейшей инженерной работы.

## Найдено и исправлено в этой волне (не «issues» — фиксирую как факт процесса)

Полный `npm run test:e2e` прогонялся впервые за весь ход 18H именно в Wave 4.
Нашёл два реальных P1-бага, оба не были видны юнит-тестам (требовали живого
браузера):

**P1a — `.dialogue-panel--cinematic` обрезала кнопку «Далее» для длинных реплик.**
`max-height: 24vh` стоял на ВСЕЙ панели (`ui.css`), а не только на тексте;
для короткой реплики влезало, для длинной (`security-baseline-path`, первая
реплика Сони — два предложения) кнопка выталкивалась за `overflow:hidden`
границу и переставала быть кликабельной, хотя визуально/в DOM оставалась
на месте. Исправлено: max-height убран с панели, остался только на
`.dialogue-text` (уже был, со своим `overflow-y:auto`) — панель теперь
всегда ровно по контенту, текст сам скроллится при необходимости.

**P1b — `cinematic.ready` мог ждать в разы дольше номинальной длительности кадра.**
Под headless software-рендером `flyTo`/`camera-controls.setLookAt()`
сходился за измеренные ~8.25с вместо ~1.1с — реплика (§5: «no line before
camera settled») блокировалась на всё это время. Исправлено:
`READY_TIMEOUT_MS=3500` в `cinematicDirector.ts` — тот же принцип
«timeout только как защита от зависания», что уже применялся в
`GATHER_TIMEOUT_MS`/`ARRIVAL_TIMEOUT_MS` этой же фичи.

Оба фикса подтверждены живым E2E-прогоном (`story-baseline.spec.ts`:
180с timeout дважды воспроизведён → зелёный за ~60-70с после обоих фиксов).
Заодно упрощён сам E2E-спек: цикл повторных кликов по маркеру убран в пользу
одного клика + одного ожидания — маркер является позиционирующимся каждый
кадр `<Html>`-оверлеем, повторный force-click во время ходьбы был лишним
риском гонки, не нужным при работающем `approaching`-guard
(`Level1StoryDecisionController.tsx`).
