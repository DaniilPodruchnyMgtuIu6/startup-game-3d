# Уточнение дорожной карты

На этой итерации не нужно добавлять пустые шкалы:

- прогресс продукта;
- мораль команды;
- стабильность;
- доверие руководства.

Пока в игре нет задач, разработчиков и управленческих событий, такие показатели не имеют реальных причин изменяться и будут являться заглушками.

Feature 02 добавляет только полноценную финансовую механику:

- стартовый бюджет;
- базовые ежедневные расходы;
- списание денег при завершении дня;
- финансовый журнал;
- финансовый итог спринта;
- предупреждения о малом остатке.

Другие показатели будут добавляться только вместе с механиками, которые на них действительно влияют.

# Цель итерации

Добавить детерминированную экономику, связанную с уже реализованным относительным временем.

После подтверждения завершения каждого активного рабочего дня игра должна:

1. рассчитать базовые расходы текущего дня;
2. один раз записать их в финансовый журнал;
3. уменьшить бюджет;
4. только после этого перевести игру к следующему дню или в `review`.

Простое перемещение по офису, диалоги, ожидание и открытие интерфейсов денег не расходуют.

# 1. Чистая финансовая модель

Создай чистый модуль финансовых правил.

Рекомендуемое имя:

`src/game/economyRules.ts`

Допустимо другое расположение, если оно лучше соответствует существующей структуре проекта.

Минимальные типы:

```ts
export type MoneyTransactionKind = "income" | "expense";

export type MoneyTransactionCategory =
  | "funding"
  | "operations";

export type ExpenseBreakdownItem = {
  code: string;
  title: string;
  amount: number;
};

export type MoneyTransaction = {
  id: string;
  kind: MoneyTransactionKind;
  category: MoneyTransactionCategory;
  title: string;
  amount: number;
  sprintNumber: number;
  day: number;
  breakdown?: ExpenseBreakdownItem[];
};
```

Правила типов:

- `amount` всегда положительное целое число;
- знак определяется полем `kind`;
- отрицательные `amount` запрещены;
- `sprintNumber` начинается с 1;
- `day` находится в диапазоне 1–10;
- не добавлять реальные даты и время;
- не использовать `Date.now()` для идентичности игровых операций;
- идентификаторы обязательных операций должны быть детерминированными.

# 2. Источник истины для бюджета

Финансовый журнал должен быть источником истины.

Рекомендуемая модель:

```ts
type EconomyState = {
  transactions: MoneyTransaction[];
};
```

Текущий бюджет вычисляется из транзакций:

```ts
export function calculateBalance(
  transactions: MoneyTransaction[]
): number;
```

Правило:

```text
доходы увеличивают баланс;
расходы уменьшают баланс.
```

Не хранить одновременно изменяемые `balance` и `transactions`, если это создаёт два независимых источника истины.

Если по архитектуре проекта принято хранить вычисленный `balance`, Claude Code обязан гарантировать его согласованность с журналом и объяснить решение. Предпочтителен расчёт из журнала.

# 4. Транзакция ежедневных расходов

Для каждого активного рабочего дня создаётся одна агрегированная транзакция.

Пример для спринта 1, дня 1:

```ts
{
  id: "operations:sprint-1:day-1",
  kind: "expense",
  category: "operations",
  title: "Базовые расходы за рабочий день",
  amount: 20_000,
  sprintNumber: 1,
  day: 1,
  breakdown: [
    {
      code: "office-rent",
      title: "Аренда офиса",
      amount: 8_000,
    },
    {
      code: "infrastructure",
      title: "Серверы и сервисы",
      amount: 4_000,
    },
    {
      code: "project-manager",
      title: "Проджект-менеджер",
      amount: 6_000,
    },
    {
      code: "administration",
      title: "Административные расходы",
      amount: 2_000,
    },
  ],
}
```

Требования:

- одна транзакция на один игровой день;
- `amount` равен сумме `breakdown`;
- транзакция создаётся для дня, который игрок завершает;
- транзакция дня 10 создаётся до перехода в `review`;
- переход из `review` в следующий `planning` не создаёт расходов;
- запуск спринта из `planning` не создаёт расходов;
- отмена подтверждения дня не создаёт расходов.

# 5. Идемпотентность

Повторный вызов расчёта одного и того же дня не должен списывать деньги повторно.

Детерминированный идентификатор:

```ts
operations:sprint-{sprintNumber}:day-{day}
```

Перед добавлением транзакции необходимо проверить, существует ли её `id`.

Если существует:

- не добавлять копию;
- не менять бюджет второй раз;
- вернуть результат, по которому можно понять, что операция уже была применена.

Добавь чистую функцию, например:

```ts
export function createDailyOperatingExpense(
  sprintNumber: number,
  day: number
): MoneyTransaction;

export function appendTransactionOnce(
  transactions: MoneyTransaction[],
  transaction: MoneyTransaction
): {
  transactions: MoneyTransaction[];
  applied: boolean;
};
```

Названия могут отличаться, но поведение должно быть таким же.

Идемпотентность обязательна даже при том, что UI обычно не позволяет нажать подтверждение дважды.

# 7. Связь с завершением рабочего дня

В проекте должна быть одна игровая операция, которая окончательно подтверждает рабочий день.

Предпочтительное смысловое имя:

```ts
completeWorkday()
```

Точное расположение зависит от реализации Feature 01.

Эта операция должна:

1. прочитать текущий `sprintNumber`;
2. прочитать текущий `day`;
3. убедиться, что спринт находится в `active`;
4. убедиться, что подтверждение дня сейчас допустимо;
5. применить расходы текущего дня;
6. продвинуть sprint-state;
7. вернуть результат операции.

Псевдокод:

```ts
function completeWorkday(): CompleteWorkdayResult {
  const sprint = getCurrentSprintState();

  if (!canCompleteCurrentWorkday(sprint)) {
    return {
      completed: false,
      reason: "invalid-sprint-state",
    };
  }

  const economyResult = applyDailyOperatingExpense(
    sprint.sprintNumber,
    sprint.day
  );

  confirmSprintDay();

  return {
    completed: true,
    economyApplied: economyResult.applied,
    chargedAmount: economyResult.transaction.amount,
  };
}
```

Это псевдокод, а не требование создать глобальный менеджер.

## Важно

Финансовую математику нельзя размещать в React-компоненте кнопки.

React-компонент может вызвать одну операцию завершения дня и отобразить результат.

Нельзя оставлять другой обычный UI-путь, который продвигает день без расчёта расходов.

Низкоуровневый `confirmEndDay`, если он остаётся публично доступным в store, не должен использоваться компонентами напрямую в обход финансового расчёта.

Не создавай универсальный event bus или scheduler. На текущем этапе нужна только узкая операция завершения дня.

# 8. Порядок выполнения

Расходы относятся к текущему завершаемому дню.

Пример:

```text
Текущее состояние:
Спринт 1, день 3
Баланс: 2 460 000 ₽
```

Игрок подтверждает завершение дня.

Результат:

```text
Создана транзакция:
Спринт 1, день 3
−20 000 ₽

Новое состояние:
Спринт 1, день 4
Баланс: 2 440 000 ₽
```

Для дня 10:

```text
Текущее состояние:
Спринт 1, день 10
```

После подтверждения:

1. списываются расходы дня 10;
2. игра переходит в `review`;
3. расходы первого спринта равны 200 000 ₽.

# 13. Предупреждения о состоянии бюджета

Добавь только информационные предупреждения.

## Низкий бюджет

Если после предполагаемого списания останется меньше стоимости двух полных базовых спринтов:

```ts
remainingBalance < BASE_SPRINT_COST * 2
```

Покажи в окне подтверждения:

> Внимание: базового бюджета осталось менее чем на два спринта.

## Критический бюджет

Если после предполагаемого списания останется меньше стоимости одного полного базового спринта:

```ts
remainingBalance < BASE_SPRINT_COST
```

Покажи:

> Критический остаток: базового бюджета не хватит на полный следующий спринт.

## Исчерпанный бюджет

Если баланс равен нулю или отрицательный:

> Бюджет проекта исчерпан.

На этой итерации это только состояние интерфейса.

Не добавлять:

- автоматическое поражение;
- увольнение;
- блокировку перехода дня;
- срочное финансирование;
- кредиты;
- звонок CEO;
- наказание совета директоров.

Поражение из-за банкротства будет отдельной фичей.

# 14. Сохранение и миграция

Финансовое состояние должно сохраняться в `localStorage` через принятый в проекте механизм Zustand persist.

При перезагрузке должны восстанавливаться:

- все транзакции;
- текущий вычисленный баланс;
- финансовый итог уже завершённых дней.

## Старое сохранение после Feature 01

В старом сохранении economy-state отсутствует.

При первом запуске после обновления необходимо создать корректное начальное состояние:

- одна транзакция стартового финансирования;
- баланс 2 500 000 ₽.

Существующий sprint-state и другой игровой прогресс не сбрасывать.

## Повреждённое финансовое сохранение

Безопасно обработай:

- повреждённый JSON;
- отсутствие массива транзакций;
- неизвестные поля;
- отрицательные `amount`;
- `NaN`;
- дробные суммы;
- неизвестный `kind`;
- дубли обязательных транзакций;
- отсутствие стартового финансирования.

Предпочтительный безопасный подход:

- валидировать и нормализовать данные;
- при полностью непригодном economy-state сбросить только экономику;
- не сбрасывать весь игровой прогресс;
- не допускать падения приложения.

Не подключать внешнюю schema-validation библиотеку только ради этой фичи, если её ещё нет в проекте.

# 15. Согласование старых sprint-сохранений

Возможна ситуация:

- игрок уже дошёл до нескольких дней или спринтов в Feature 01;
- финансовой механики тогда ещё не было.

Не нужно задним числом списывать деньги за все ранее прожитые дни.

После установки Feature 02:

- игрок получает стартовый бюджет;
- расходы начинают применяться со следующего подтверждённого дня;
- уже пройденные до обновления дни не восстанавливаются как финансовые транзакции.

Это упрощённое правило миграции должно быть описано в итоговом ответе Claude Code.

Не пытайся угадывать историю старого прохождения.

# 16. Сброс прогресса

Существующий общий сброс через `?intro` должен также сбрасывать экономику.

После сброса:

- журнал снова содержит только стартовое финансирование;
- баланс равен 2 500 000 ₽;
- старые расходные транзакции удалены;
- sprint-state сброшен по правилам Feature 01;
- существующее поведение пролога сохранено.

Не добавляй второй независимый обработчик `?intro`.

Расширь общую существующую точку сброса.

# 19. Требования к тестам

Добавь unit-тесты чистой финансовой логики.

Минимальный набор:

1. начальный журнал содержит одну транзакцию финансирования;
2. начальный баланс равен 2 500 000 ₽;
3. сумма breakdown ежедневных расходов равна 20 000 ₽;
4. стоимость полного спринта равна 200 000 ₽;
5. расход дня 1 уменьшает баланс на 20 000 ₽;
6. повторное применение расхода того же дня не меняет баланс;
7. расходы разных дней применяются отдельно;
8. после 10 дней расходы спринта равны 200 000 ₽;
9. расход дня 10 применяется до перехода в `review`;
10. `planning` не создаёт расход;
11. переход из `review` в следующий спринт не создаёт расход;
12. отмена подтверждения дня не создаёт расход;
13. форматирование рублей соответствует примерам;
14. низкий и критический пороги определяются корректно;
15. старое сохранение без economy-state получает стартовое финансирование;
16. повреждённое economy-сохранение не ломает приложение;
17. общий reset возвращает начальную экономику;
18. review показывает фактические расходы текущего спринта;
19. единственная UI-операция подтверждения дня использует финансовый расчёт.

Если тестирование React-компонента для пункта 19 слишком хрупкое, протестируй use-case завершения дня отдельно с контролируемыми store-состояниями.

Не поднимать полноценную Three.js-сцену, если можно проверить чистую логику и store.

# 21. Ручной сценарий приёмки

## Сценарий 1. Новая игра

1. Открыть игру с `?intro`.

7. Убедиться, что бюджет остался 2 500 000 ₽.
8. Убедиться, что расходной транзакции нет.

1. Повторно открыть подтверждение.

1. Походить по офису.
2. Поговорить с NPC.
3. Открыть и закрыть доску задач.
4. Подождать.
5. Убедиться, что день и бюджет не изменились.

1. Последовательно завершить все 10 дней.
2. Убедиться, что после дня 10 открылись итоги.
3. Убедиться, что расходы спринта равны 200 000 ₽.
4. Убедиться, что остаток равен 2 300 000 ₽.

## Сценарий 6. Следующий спринт

1. Нажать переход к следующему спринту.

3. Начать второй спринт.

2. Запомнить бюджет и последние транзакции.
3. Перезагрузить страницу.
4. Убедиться, что бюджет и журнал восстановились.
5. Завершить следующий день.
6. Убедиться, что предыдущий день не был списан повторно.

## Сценарий 8. Сброс

1. Иметь несколько расходных операций.
2. Открыть игру с `?intro`.
3. Убедиться, что журнал снова содержит только стартовое финансирование.

6. Убедиться, что существующая кат-сцена не списывает деньги сама по себе.

# 22. Критерии готовности

Feature 02 считается завершённой только если:

- начальный бюджет равен 2 500 000 ₽;
- журнал содержит стартовое финансирование;
- каждый подтверждённый активный день стоит 20 000 ₽;
- отмена не списывает деньги;
- один день нельзя списать дважды;
- день 10 списывается до `review`;
- полный спринт стоит 200 000 ₽;
- бюджет отображается в HUD;
- финансовая панель показывает breakdown и журнал;
- review показывает фактические расходы спринта;
- деньги и журнал сохраняются после перезагрузки;
- старое сохранение Feature 01 поддерживается;
- `?intro` сбрасывает экономику;
- бездействие, перемещение и диалоги не расходуют бюджет;
- отрицательный баланс пока не вызывает game over;
- не реализованы механики Feature 03 и следующих этапов;
- тесты проходят;
- production-сборка проходит;
- существующие механики игры не сломаны.
