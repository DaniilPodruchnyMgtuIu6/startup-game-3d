# Цель итерации

Сделать существующую сцену `security-breach` частью нормального прохождения.

Сцена должна:

- автоматически стать доступной после появления первого рабочего прототипа;
- запускаться не сразу в момент завершения prototype-задачи;
- запускаться только в подходящий активный рабочий день;
- не перебивать другие сцены, мини-игры и интерфейсы;

- корректно переживать сохранение и перезагрузку;
- сохранять выбор игрока;
- не применять выговор и сюжетную задачу повторно;
- по-прежнему поддерживать ручной dev-запуск.

# 1. Сюжетное место события

Сцена происходит после того, как:

1. игрок собрал техническую команду;
2. Кирилл и Алина уже работают в офисе;
3. команда создала первый рабочий прототип OfficeFlow;
4. закончился как минимум один полный спринт;
5. разработка продолжается в следующем активном спринте.

Смысл:

> Пока продукт был только идеей, нарушения безопасности казались мелочью. Теперь в офисе есть рабочие учётные записи, серверы и данные, поэтому незаблокированный компьютер становится реальным риском.

Сцена не должна происходить до появления разработчиков или прототипа.

---

# 2. Точное правило автоматического запуска

Сцена может быть автоматически запущена, только если одновременно выполнены все условия:

```ts
type SecurityBreachTriggerContext = {
  gamePhase: "free";
  sprintPhase: "active";
  sprintNumber: number;
  day: number;
  hasBackendDeveloper: boolean;
  hasFrontendDeveloper: boolean;
  hasFirstPrototype: boolean;
  securityBreachStatus: SecurityBreachStatus;
  isCutsceneRunning: boolean;
  isServerMinigameOpen: boolean;
  isBlockingOverlayOpen: boolean;
  isBlockingDialogueOpen: boolean;
};
```

Обязательные условия:

```text
gamePhase === free
sprintPhase === active
sprintNumber >= 2
day >= 2
Кирилл нанят
Алина нанята
первый прототип готов
security-breach ещё не завершена
другая кат-сцена не запущена
серверная мини-игра не открыта
блокирующий UI не открыт
блокирующий диалог не открыт
```

## Почему `sprintNumber >= 2`

Игрок должен завершить хотя бы один полный спринт до внутреннего аудита.

## Почему `day >= 2`

Сцена не должна начинаться сразу после кнопки `Начать спринт`.

Игрок получает хотя бы один обычный рабочий день нового спринта.

## Примеры

### Прототип готов в первом спринте

```text
Спринт 1, день 8:
прототип готов

Спринт 1:
сцена не запускается

Спринт 2, день 1:
сцена не запускается

После завершения дня 1:
начинается день 2

После закрытия ежедневного отчёта:
сцена запускается автоматически
```

### Прототип готов во втором спринте, день 5

После расчёта дня 5 начинается день 6.

После закрытия ежедневного отчёта сцена может запуститься, если остальные блокеры отсутствуют.

### Прототип готов во втором спринте, день 1

После завершения дня 1 и закрытия отчёта начинается день 2, затем запускается сцена.

### Прототип готов в review

Сцена ждёт:

1. завершения review;
2. planning;
3. начала следующего спринта;
4. завершения первого дня;
5. закрытия ежедневного отчёта.

# 3. Чистое правило eligibility

Создай чистый модуль.

Рекомендуемое имя:

`src/game/securityStoryRules.ts`

Минимальная функция:

```ts
export function canTriggerSecurityBreach(
  context: SecurityBreachTriggerContext
): boolean;
```

Функция:

- не читает Zustand напрямую;
- не запускает кат-сцену;
- не изменяет store;
- возвращает только boolean;
- покрывается unit-тестами.

Допустимо вернуть структурированный результат:

```ts
export type SecurityBreachEligibility = {
  allowed: boolean;
  blockingReasons: SecurityBreachBlockingReason[];
};
```

Это предпочтительно, если проект уже использует такой стиль.

Не создавать универсальный rule engine.

---

# 4. Состояние сюжетной сцены

Создай отдельный небольшой Zustand-store.

Рекомендуемое имя:

`src/game/securityStoryStore.ts`

## Типы

```ts
export type SecurityBreachStatus =
  | "not-started"
  | "running"
  | "completed";

export type SecurityBreachDecision =
  | "take-responsibility"
  | "blame-project-manager";

export type StoryMoment = {
  sprintNumber: number;
  day: number;
};

export type SecurityStoryState = {
  securityBreach: {
    status: SecurityBreachStatus;
    firstStartedAt?: StoryMoment;
    completedAt?: StoryMoment;
    decision?: SecurityBreachDecision;
    effectsApplied: boolean;
  };

  markSecurityBreachRunning(moment: StoryMoment): void;

  resolveSecurityBreachDecision(
    decision: SecurityBreachDecision
  ): ResolveSecurityDecisionResult;

  markSecurityBreachCompleted(moment: StoryMoment): void;

  markSecurityBreachFailed(): void;

  resetSecurityStory(): void;
};
```

Названия могут быть адаптированы к стилю проекта.

## Начальное состояние

```ts
{
  securityBreach: {
    status: "not-started",
    effectsApplied: false,
  },
}
```

## Правила

- `firstStartedAt` записывается только при первом запуске;
- повторный старт не перезаписывает первый момент;
- `decision` записывается один раз;
- если решение уже сохранено, повторный вызов не меняет его;
- `effectsApplied` защищает побочные эффекты;
- `completed` является финальным состоянием;
- completed-сцена автоматически больше не запускается.

Не добавлять состояние будущих аудитов или безопасника.

# 5. Единственный автоматический trigger

Добавь один явный координатор.

Рекомендуемые варианты:

- `SecurityStoryTrigger.tsx`;
- `useSecurityStoryTrigger.ts`.

Выбери вариант, соответствующий существующей архитектуре.

Он должен:

1. подписаться только на необходимые селекторы;
2. дождаться hydration нужных store;
3. собрать trigger context;
4. вызвать чистое eligibility-правило;
5. при `allowed === true` запустить use-case сцены;
6. не запускать сцену повторно на каждом render;
7. не содержать сценарных диалогов;
8. не создавать общий event engine.

## Место подключения

Подключи trigger один раз на верхнем игровом уровне, где уже доступны:

- состояние приложения;
- cutscene system;
- оверлеи;
- stores.

Не подключай его:

- внутри каждого NPC;
- внутри whiteboard;
- внутри daily report;
- внутри HUD-кнопки;
- внутри `completeWorkday`.

`completeWorkday` только изменяет состояния. Trigger наблюдает их и запускает сцену, когда UI становится свободен.

# 6. Момент запуска после ежедневного отчёта

После завершения дня порядок должен быть таким:

1. рассчитывается product progress;
2. списываются расходы;
3. sprint day продвигается;
4. показывается ежедневный отчёт;
5. trigger видит eligibility, но не запускает сцену, потому что отчёт является blocking overlay;
6. игрок нажимает `Продолжить`;
7. отчёт закрывается;
8. trigger повторно проверяет eligibility;
9. сцена запускается.

Не закрывай daily report автоматически.

Не запускай сцену под daily report.

Если после закрытия отчёта должен открыться review, review имеет приоритет и сцена ждёт следующего активного спринта.

# 7. Use-case запуска сцены

Создай узкую операцию, например:

```ts
export async function tryStartSecurityBreach(
  context: SecurityBreachTriggerContext
): Promise<TryStartSecurityBreachResult>;
```

Она должна:

1. повторно проверить eligibility непосредственно перед стартом;
2. атомарно или последовательно безопасно отметить status `running`;
3. вызвать существующую сцену из registry;
4. дождаться завершения;
5. отметить status `completed`;
6. при ошибке вернуть status в `not-started`;
7. не проглатывать ошибку без логирования.

Рекомендуемый результат:

```ts
export type TryStartSecurityBreachResult =
  | {
      started: true;
      completed: true;
    }
  | {
      started: false;
      reason:
        | "not-eligible"
        | "already-running"
        | "already-completed";
    }
  | {
      started: true;
      completed: false;
      reason: "scene-failed";
    };
```

Не создавай универсальный `StoryManager`.

# 10. Идемпотентные побочные эффекты выбора

Существующая сцена уже может:

- увеличить `reprimands`, если игрок обвиняет Соню;
- добавить задачу регулярного обучения безопасности.

Эти эффекты должны применяться ровно один раз.

Создай узкую операцию, например:

```ts
export function applySecurityBreachDecisionOnce(
  decision: SecurityBreachDecision
): ApplySecurityDecisionResult;
```

## Для `take-responsibility`

- сохранить decision;
- не добавлять выговор;
- добавить существующую задачу обучения безопасности, если сцена уже делает это;
- отметить effectsApplied.

## Для `blame-project-manager`

- сохранить decision;
- добавить ровно один выговор;
- добавить задачу обучения безопасности;
- отметить effectsApplied.

## Требования

- повторный вызов не добавляет второй выговор;
- повторный вызов не создаёт дубликат задачи;
- задача имеет стабильный id;
- если задача уже существует, использовать её;
- если effects уже applied, вернуть `applied: false`;
- не добавлять штрафы;
- не менять мораль;
- не менять бюджет;
- не запускать аудитную систему.

Если текущий код применяет эффекты прямо внутри веток сцены, вынеси только минимальную идемпотентную операцию и вызови её из сцены.

# 11. Поведение при перезагрузке во время сцены

Кат-сцена не обязана продолжаться с точного кадра после reload.

Но игра не должна застревать.

## Hydration-правило

Если из сохранения получено:

```ts
status: "running"
```

нормализуй его в:

```ts
status: "not-started"
```

Сохрани при этом:

- `firstStartedAt`;
- `decision`, если он уже был записан;
- `effectsApplied`.

После загрузки сцена сможет запуститься снова при eligibility.

## Если decision уже сохранён

При повторном запуске:

- не показывай choice повторно;
- используй сохранённое решение;
- не применяй эффекты повторно;
- продолжи оставшуюся часть сцены;
- в конце пометь сцену completed.

Если безопасно пропустить choice в текущей архитектуре невозможно, допустимо повторно показать выбор, но:

- первый сохранённый decision остаётся источником истины;
- новый выбор не изменяет decision;
- эффекты не повторяются.

Предпочтителен первый вариант.

# 12. Ручной dev-запуск

Сохрани:

```js
window.__startCutscene("security-breach")
```

Ручной запуск должен использовать тот же жизненный цикл сцены:

- mark running;
- сохранить decision;
- применить эффекты once;
- mark completed.

Это предотвращает автоматический повтор после ручного теста.

## Dev-особенность

Если сцену вручную запустили до выполнения сюжетных условий:

- разрешить запуск в dev;
- после успешного завершения считать её completed;
- автоматический trigger больше её не запускает.

Не добавляй отдельную production-кнопку запуска.

# 13. Что происходит после сцены

После успешного завершения:

- status становится `completed`;
- сохраняется completedAt;
- игрок возвращается к свободному управлению;
- сцена больше автоматически не запускается;
- существующая задача обучения безопасности видна на доске;
- существующий выговор сохранён, если был выбран blame;
- никакой новый обязательный разговор не начинается;
- безопасник не появляется;
- аудиторы не остаются как постоянные NPC.

В Feature 06 после сцены появится отдельный повод поговорить с Соней.

# 14. UI и визуальное поведение

Не добавляй новый постоянный HUD-индикатор сюжетного status.

В офис пришли представители внутреннего аудита

- не требует отдельного подтверждения;
- не двигает время;
- не создаёт задержку, зависящую от реальных минут;
- не перекрывает уже открытый UI;
- используется только если в проекте уже есть подходящий toast/banner.

Не создавай новую систему toast только ради этой строки.

Сама кат-сцена должна оставаться главным визуальным событием.

# 15. Сохранение и миграция

Security-story state сохраняется через существующий Zustand persist.

После reload восстанавливаются:

- completed status;
- firstStartedAt;
- completedAt;
- decision;
- effectsApplied.

## Старое сохранение Feature 04

В старом сохранении security-story state отсутствует.

Добавь начальное состояние:

```ts
{
  securityBreach: {
    status: "not-started",
    effectsApplied: false,
  },
}
```

Не сбрасывай:

- sprint;
- budget;
- team;
- product progress;
- prototype milestone;
- reprimands;
- existing department tasks.

Если условия уже выполнены в старом сохранении:

- сцена запускается при следующем безопасном idle-моменте;
- только если active, sprint >= 2 и day >= 2.

## Повреждённое сохранение

Безопасно обработай:

- неизвестный status;
- неизвестный decision;
- completed без completedAt;
- effectsApplied без decision;
- отрицательные sprint/day;
- day вне диапазона 1–10;
- duplicated/malformed data.

Нормализация должна:

- не падать;
- не сбрасывать другие stores;
- не создавать второй выговор;
- не создавать дубликат задачи;
- completed считать финальным только при валидном состоянии;
