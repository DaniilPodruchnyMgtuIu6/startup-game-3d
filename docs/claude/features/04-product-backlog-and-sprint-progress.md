# Цель итерации

Добавить первый полноценный цикл разработки OfficeFlow:

1. в фазе `planning` игрок подходит к физическому whiteboard;
2. выбирает задачи из фиксированного backlog;
3. формирует отдельную очередь Кирилла и Алины;
4. видит плановую загрузку каждого разработчика;
5. запускает спринт с доски;
6. при завершении каждого рабочего дня разработчики получают детерминированный прогресс;
7. игрок видит отчёт за день;
8. задачи завершаются и сохраняются;
9. в review показывается результат спринта;
10. незавершённые задачи можно перепланировать в следующем спринте;
11. после завершения шести основных задач появляется первый рабочий прототип OfficeFlow.

Эта фича создаёт детерминированное ядро разработки.

Случайные проблемы, конфликты, усталость, аудит и риски появятся позже.

# 4. Состояние разработки продукта

Создай отдельный Zustand-store.

Рекомендуемое имя:

`src/game/productStore.ts`

## Минимальные типы

```ts
export type ProductTaskStatus =
  | "backlog"
  | "planned"
  | "in-progress"
  | "done";

export type ProductTaskState = {
  taskId: string;
  status: ProductTaskStatus;
  progressDays: number;
  plannedSprintNumber?: number;
  planOrder?: number;
  completedAt?: {
    sprintNumber: number;
    day: number;
  };

export type WorkdayEmployeeProgress = {
  employeeId: string;
  taskId?: string;
  beforeProgressDays?: number;
  afterProgressDays?: number;
  completedTask?: boolean;
  idleReason?: "no-planned-task" | "all-planned-tasks-done";

export type WorkdayProgressRecord = {
  id: string;
  sprintNumber: number;
  day: number;
  employeeResults: WorkdayEmployeeProgress[];

```

Store должен поддерживать:

- добавление задачи в текущий planning;
- удаление задачи из planning;
- изменение порядка;
- применение одного рабочего дня прогресса;
- подготовку незавершённых задач к следующему planning;
- reset.

Названия методов адаптируй к стилю проекта.

# 8. Плановая загрузка

Один разработчик имеет базовую вместимость:

```ts
export const EMPLOYEE_SPRINT_CAPACITY_DAYS = 10;
```

Загрузка считается по оставшейся, а не исходной трудоёмкости.

Состояния:

```text
0–8 дней   -> нормальная загрузка
9–10 дней  -> полная загрузка
более 10   -> перегрузка
```

Перегрузка не запрещает запуск спринта.

Покажи предупреждение:

> План превышает доступные 10 рабочих дней. Часть задач может перейти в следующий спринт.

Это осознанное управленческое решение игрока.

# 11. Детерминированный прогресс рабочего дня

Каждый нанятый разработчик создаёт максимум **1 рабочий день прогресса** за одно подтверждённое завершение игрового дня.

Прогресс не зависит от:

- реального времени;
- текущей анимации;
- случайного числа;
- нахождения игрока рядом;
- ответа DeepSeek.

## Алгоритм для каждого разработчика

1. получить задачи текущего спринта;
2. отсортировать по `planOrder`;
3. найти первую незавершённую задачу;
4. увеличить `progressDays` на 1;
5. если достигнут `effortDays`, отметить задачу `done`;
6. записать `completedAt`;
7. не переходить к следующей задаче в тот же день.

Один сотрудник не может сделать две единицы работы за день.

Если задач нет, прогресс отсутствует, но зарплата всё равно списывается.

- вернуть существующий результат;
- `applied` должен быть `false`.

# 14. Отчёт о завершённом дне

После подтверждения дня открой блокирующий оверлей:

```text
Итоги дня 3
```

Для каждого разработчика покажи результат.

Пример:

```text
Кирилл Морозов
API авторизации: 2/3 → 3/3
Задача завершена
```

```text
Алина Белова
Каталог переговорных: 1/3 → 2/3
```

При отсутствии работы:

```text
Нет назначенных задач. День прошёл без прогресса.
```

Общий результат:

```text
Готовность OfficeFlow: 11% → 16%
Расходы за день: 37 000 ₽
Остаток бюджета: 2 389 000 ₽
```

Кнопка: `Продолжить`.

Закрытие отчёта не двигает время и не повторяет расчёт.

Если завершён день 10, после закрытия виден review.

# 15. Расчёт готовности продукта

Готовность OfficeFlow рассчитывается по трудоёмкости всех 14 задач.

Формула:

```text
сумма зачтённого progressDays / 45 × 100
```

Требования:

- учитывать частично выполненные задачи;
- диапазон 0–100;
- целое число;
- округление вниз через `Math.floor`;
- неизвестные task ids не учитываются;
- progress ограничивается effortDays.

Примеры:

```text
0 из 45 дней     -> 0%
1 из 45 дней     -> 2%
17 из 45 дней    -> 37%
45 из 45 дней    -> 100%
```

```ts
getFirstPrototypeCompletion(taskStates)
```

Дата milestone равна наиболее позднему `completedAt` среди шести задач.

В дневном отчёте, где завершена последняя задача, покажи:

```text
Первый рабочий прототип OfficeFlow готов
```

Описание:

> Команда собрала вход, каталог переговорных и бронирование в единый рабочий сценарий.

Не запускать сцену с незаблокированным монитором в этой итерации.

# 17. Видимый mock-продукт

После достижения первого прототипа на вкладке разработки появляется кнопка:

```text
Открыть прототип
```

Открывается простой UI-макет OfficeFlow:

- экран входа;
- список из трёх переговорных;
- выбор времени;
- подтверждение бронирования.

Mock не должен:

- обращаться к backend;
- хранить отдельные пользовательские данные;
- создавать настоящую систему бронирований;
- тратить день;
- менять бюджет;
- использовать iframe или внешний сайт.

До milestone кнопка заблокирована:

```text
Прототип станет доступен после завершения основных задач.
```

# 19. Переход к следующему planning

Создай или расширь единую операцию:

```ts
completeSprintAndPrepareNextPlanning()
```

Она должна:

1. проверить phase `review`;
2. оставить completed tasks как `done`;
3. вернуть incomplete tasks в `backlog`;
4. сохранить их `progressDays`;
5. очистить `plannedSprintNumber` и `planOrder`;
6. продвинуть sprint-store к следующему `planning`;
7. не списывать деньги;
8. не применять progress.

Review-компонент не должен обходить эту операцию.

# 20. Поведение разработчиков на карте

- использовать существующий planner или его hook;
- не создавать параллельный scheduler;
- не телепортировать NPC;
- не связывать progress с длительностью анимации.

Рекомендуемый вес:

```text
work: 0.70
остальные активности: суммарно 0.30
```

При выборе или наведении на разработчика допустим компактный статус:

```text
API авторизации · 2/3
```

Не показывать постоянные большие подписи.

# 21. Сохранение и миграция

Product-state сохраняется через Zustand persist.

Восстанавливаются:

- progress;
- statuses;
- текущий plan;
- порядок;
- completedAt;
- workday history;
- prototype availability.

## Старые сохранения Feature 03

Если product-state отсутствует:

- создать начальные 14 задач;
- не сбрасывать другие stores;
- не начислять progress задним числом;
- active-сохранение без плана продолжает работать;
- завершение дня даёт idle result и списывает зарплату.

## Повреждённое сохранение

Нормализуй:

- неизвестные и повторяющиеся task ids;
- отсутствующие каталоговые задачи;
- отрицательный или слишком большой progress;
- неизвестный status;
- неверный sprint/order;
- повторяющиеся workday ids.

Не сбрасывай другие stores.

# 22. Общий reset

`?intro` должен также сбрасывать product-state.

После reset:

- 14 задач снова в backlog;
- progress равен 0;
- plan пуст;
- history пуст;
- готовность 0%;
- prototype недоступен;
- остальные stores сброшены по своим правилам.

Не добавляй второй URL-handler.

- поражение и победу;

- универсальный workflow engine;

Для порядка достаточно кнопок `Вверх` и `Вниз`.

## Planning через карту

1. Добавить только backend-задачу.
2. Убедиться, что start запрещён без frontend.
3. Добавить frontend-задачу.
4. Проверить нагрузку.
5. Запустить sprint.

## Первый день

1. Завершить день.
2. Увидеть daily report.
3. Увидеть +1 progress Кирилла и Алины.
4. Увидеть расход 37 000 ₽.
5. Проверить read-only board.

## Перегрузка и перенос

1. Запланировать >10 дней одному сотруднику.
2. Получить warning.
3. Завершить sprint.
4. Увидеть incomplete task.
5. Перейти в новый planning.
6. Увидеть задачу в backlog с сохранённым progress.
7. Убедиться, что нагрузка равна оставшимся дням.

## Первый prototype

1. Завершить все шесть prototype-задач.
2. Увидеть milestone в daily report.
3. Увидеть готовность 37%.

6. Убедиться, что время и бюджет не изменились.
7. Убедиться, что security cutscene не запустилась автоматически.

## Сохранение и reset

2. Перезагрузить.
3. Проверить отсутствие дублей.
4. Открыть с `?intro`.

- движение;
- NPC и claims;
- панель команды;
- финансы;
- задачи отдела;
- серверные мини-игры;
