# Цель итерации

После завершения внутреннего аудита игрок должен лично подойти к Соне и обсудить дальнейшие действия.

Игрок принимает одно из двух решений:

1. одобрить найм штатного специалиста по информационной безопасности;
2. отказаться от найма и продолжить без отдельного безопасника.

Feature 06 должна:

- создать обязательный post-audit objective;
- показать маркер разговора над Соней;
- заставить игрока физически подойти к ней;
- изменить тон разговора в зависимости от выбора в `security-breach`;
- сохранить кадровое решение;
- применить его последствия ровно один раз;
- заблокировать завершение рабочего дня, пока разговор не завершён;
- подготовить состояние для Feature 07 и Feature 08.

Feature 06 не добавляет самого безопасника, его модель, зарплату, повторные аудиты или штрафы.

# 1. Сюжетный поток

Полный поток после Feature 06:

```text
Первый прототип готов
        ↓
Во втором или более позднем спринте запускается security-breach
        ↓
Игрок принимает решение в сцене
        ↓
Сцена завершается
        ↓
Над Соней появляется маркер обязательного разговора
        ↓
Игрок подходит к Соне
        ↓
Обсуждает результаты аудита
        ↓
Решает: нанимать безопасника или отказаться
        ↓
Решение сохраняется
        ↓
Игрок снова может завершать рабочие дни
```

Разговор не должен начинаться автоматически сразу после кат-сцены.

Игрок должен получить управление и самостоятельно подойти к Соне.

# 2. Расширение story-state

Расширь существующий `securityStoryStore`, а не создавай новый store.

## Типы

```ts
export type PostAuditConversationStatus =
  | "locked"
  | "pending"
  | "running"
  | "completed";

export type SecurityStaffingDecision =
  | "approve-security-hire"
  | "decline-security-hire";

export type SecurityStoryState = {
  securityBreach: {
    // существующее состояние Feature 05
  };

  postAuditConversation: {
    status: PostAuditConversationStatus;
    startedAt?: StoryMoment;
    completedAt?: StoryMoment;
    staffingDecision?: SecurityStaffingDecision;
    effectsApplied: boolean;
  };

  unlockPostAuditConversation(): void;

  markPostAuditConversationRunning(
    moment: StoryMoment
  ): StoryTransitionResult;

  resolveSecurityStaffingDecision(
    decision: SecurityStaffingDecision
  ): ResolveSecurityStaffingResult;

  markPostAuditConversationCompleted(
    moment: StoryMoment
  ): StoryTransitionResult;

  markPostAuditConversationFailed(): void;

  resetSecurityStory(): void;
};
```

Названия могут быть адаптированы к текущему стилю проекта.

## Начальное состояние новой игры

```ts
{
  postAuditConversation: {
    status: "locked",
    effectsApplied: false,
  }
}
```

## Разблокировка

После успешного завершения `security-breach`:

```ts
postAuditConversation.status = "pending";
```

Разблокировка должна быть идемпотентной.

Повторное завершение или повторная обработка сцены не должны менять:

- уже начатый разговор;
- уже завершённый разговор;
- staffing decision;
- effectsApplied.

# 7. Интеракция с Соней

Повтори принцип существующего знакомства с Соней.

При клике на Соню во время `pending`:

1. игрок строит маршрут к Соне;
2. Соня прекращает автономную активность;
3. story planner Сони ставится на паузу;
4. игрок и Соня поворачиваются друг к другу;
5. только после достижения допустимой дистанции начинается диалог;
6. во время диалога движение игрока блокируется;
7. после завершения Соня возвращается к обычной автономной жизни.

## Важно

Не телепортировать игрока.

Не открывать диалог из другого конца офиса.

Не создавать отдельную механику разговора, если существующая уже подходит.

Если Соня сидит:

- допустимо начать разговор в сидячем состоянии, если существующая система поддерживает это;
- иначе корректно освободить claim и перевести её в подходящее состояние;
- не оставлять занятое рабочее место после разговора.

# 8. Eligibility разговора

Создай чистое правило.

```ts
export type PostAuditConversationContext = {
  gamePhase: string;
  sprintPhase: string;
  conversationStatus: PostAuditConversationStatus;
  securityBreachStatus: SecurityBreachStatus;
  isCutsceneRunning: boolean;
  isServerMinigameOpen: boolean;
  isBlockingOverlayOpen: boolean;
  isBlockingDialogueOpen: boolean;
};
```

Рекомендуемая функция:

```ts
export function canStartPostAuditConversation(
  context: PostAuditConversationContext
): boolean;
```

Разговор разрешён, если:

```text
game phase допускает свободное управление
security-breach completed
conversation pending
другая cutscene не запущена
server minigame закрыта
blocking overlay закрыт
blocking dialogue закрыт
```

Sprint phase может быть:

- `active`;
- `planning`.

Во время `review` разговор не начинается.

Если сцена завершилась в active, обычный ожидаемый поток — разговор в тот же игровой день.

# 9. Тон разговора в зависимости от прошлого выбора

Используй сохранённый `SecurityBreachDecision`.

Основное кадровое решение одинаково доступно в обеих ветках.

Не добавляй новую систему отношений.

## Ветка A — игрок взял ответственность

Условие:

```ts
securityBreach.decision === "take-responsibility"
```

Текст:

```text
Соня:
Спасибо, что не стали сваливать всё на одного человека.
Проблема не в одном незаблокированном компьютере.

Соня:
У нас уже есть разработчики, рабочий прототип, серверы и учётные записи.
Но за безопасность системно никто не отвечает.

Соня:
Я считаю, нам нужен отдельный специалист по информационной безопасности.
Он будет разбирать замечания аудита, проводить обучение и проверять новые решения до релиза.
```

## Ветка B — игрок обвинил Соню

Условие:

```ts
securityBreach.decision === "blame-project-manager"
```

Текст:

```text
Соня:
После аудита вы решили сделать виноватой меня.
Но проблема не исчезнет от того, кому выдадут выговор.

Соня:
У нас есть разработчики, рабочий прототип, серверы и учётные записи.
При этом за безопасность системно никто не отвечает.

Соня:
Если мы продолжим искать крайнего после каждого нарушения,
следующая проверка закончится намного хуже.
Нам нужен отдельный специалист по информационной безопасности.
```

## Fallback

Если decision отсутствует из-за старого или повреждённого сохранения, используй нейтральную ветку:

```text
Соня:
Аудит показал, что безопасность у нас держится на случайных решениях.
Теперь у нас есть команда, прототип и данные, поэтому так продолжаться не может.
```

# 10. Главное решение игрока

После реплик Сони покажи два варианта.

## Вариант 1 — одобрить найм

Choice id:

```ts
"approve-security-hire"
```

Текст кнопки:

```text
Открываем вакансию. Нанимаем безопасника.
```

Финальная реплика Сони:

```text
Хорошо. Я подготовлю требования к вакансии.
Но учтите: безопасник будет просить время разработчиков на исправления,
а его зарплата увеличит наши постоянные расходы.
```

Сохраняется:

```ts
staffingDecision: "approve-security-hire"
```

## Вариант 2 — отказаться

Choice id:

```ts
"decline-security-hire"
```

Текст кнопки:

```text
Нет. Пока справимся своими силами.
```

Финальная реплика Сони:

```text
Тогда замечания аудита останутся на нашей ответственности.
Если мы не успеем их закрыть, следующая проверка уже не ограничится предупреждением.
```

Сохраняется:

```ts
staffingDecision: "decline-security-hire"
```

## Запрещённый вариант

Не добавлять внешнего консультанта.

В диалоге не должно быть третьего варианта:

- привлечь консультанта;
- нанять подрядчика;
- временно отдать безопасность на аутсорс.

# 12. Завершение разговора

После применения решения:

1. conversation status становится `completed`;
2. записывается `completedAt`;
3. marker исчезает;
4. HUD objective исчезает;
5. задача разговора становится выполненной;
6. игрок снова получает управление;
7. Соня возвращается к автономной жизни;
8. завершение рабочего дня снова разрешается.

Разговор:

- не завершает день;
- не применяет product progress;
- не списывает расходы;
- не запускает review;
- не добавляет нового NPC.

# 13. Блокировка завершения рабочего дня

Пока:

```ts
postAuditConversation.status === "pending"
```

кнопка завершения рабочего дня должна быть недоступна.

Сообщение:

```text
Сначала обсудите результаты аудита с Соней.
```

Если игрок пытается вызвать use-case завершения дня в обход UI, операция должна вернуть контролируемую причину:

```ts
"required-story-conversation"
```

или эквивалент текущего стиля.

## Почему разговор блокирует день

Это обязательное управленческое решение после критического события.

Игрок может:

- ходить по офису;
- открыть доску;
- открыть финансы;
- открыть панель команды;
- осмотреть прототип;
- поговорить с Соней.

Но не может перейти к следующему рабочему дню, не определив позицию по безопасности.

## Ограничение

Блокировка действует только в `active`.

В `planning` кнопки завершения дня и так нет.

# 14. Поведение при reload во время разговора

Кат-сцена разговора не обязана продолжаться с точной реплики.

Если persist содержит:

```ts
status: "running"
```

нормализуй в:

```ts
status: "pending"
```

После reload:

- marker над Соней появляется снова;
- игрок может повторно начать разговор;
- уже сохранённое staffingDecision не перезаписывается;
- effects не применяются повторно.

## Если decision уже сохранено, но conversation не completed

При повторном разговоре:

- допустимо пропустить choice;
- использовать сохранённое решение;
- показать финальную реплику соответствующей ветки;
- завершить conversation;
- не применять effects повторно.

Предпочтительно реализовать именно это поведение.

# 26. Критерии готовности

- разговор разблокируется только после completed `security-breach`;
- разговор не начинается автоматически;

- reset очищает состояние;
