# Feature 17B — сюжетные решения безопасности и ролей

## Цель

Реализовать восемь обязательных сцен Level 1.

Каждая сцена должна иметь:

- детерминированный trigger;
- objective;
- сюжетный marker;
- статический dialogue;
- choices;
- качественное описание последствий;
- явный handler;
- immediate reaction;
- persist;
- regression tests.

Игрок не видит числовые risk impacts.

Все суммы, effort и impacts брать из `src/game/balance/`.

# 1. Проверка системы: аудит или безопасник

## ID

```text
security-baseline-path
```

## Trigger

- Кирилл нанят;
- Алина нанята;
- первый sprint ещё не начат;
- решение не принято.

## Участники

- Соня;
- Кирилл;
- Алина.

## Диалог

```text
Соня:
Команду разработки мы собрали.
Но перед стартом нужно проверить весь офис:
компьютеры, доступы, серверы и рабочие файлы.

Кирилл:
Сейчас всё работает.
Но часть настроек мы делали быстро,
и я не могу обещать, что нигде не осталось лишнего доступа.

Алина:
Мне тоже нужно понимать,
какие данные можно использовать в макетах и тестах.

Соня:
Проверку всё равно придётся провести.
Есть два пути.

Соня:
Заказать формальный аудит сейчас —
мы быстро получим список проблем,
но заплатим и отвлечёмся на исправления.

Соня:
Или сначала нанять специалиста по безопасности.
Он останется в команде,
но его зарплата станет постоянным расходом.
```

## Choices

### Заказать аудит

```text
commission-security-audit
```

Качественная подсказка:

```text
Быстрый независимый список проблем.
Потребует заметных расходов.
```

Effects:

- expense 140 000 ₽;
- category `security-audit`;
- transaction id `story:baseline-security-audit`;
- task `complete-baseline-security-audit`;
- audit result через 2 завершённых workdays;
- baseline path `external-audit`;
- governance mitigation -1;
- внешний audit actor только на сцену результата;
- Илья позже всё ещё может быть нанят, но не обязателен.

### Сначала нанять безопасника

```text
hire-security-specialist-first
```

Подсказка:

```text
Постоянный контроль и дополнительные варианты решений.
Увеличит ежедневные расходы.
```

Effects:

- task `hire-security-specialist`;
- deadline найма 3 workdays;
- после реального найма task `complete-internal-security-review`;
- review effort Ильи 2 workdays;
- baseline path `internal-review`;
- если Илья не нанят в срок: governance +2 и warning.

## Реакции

После аудита:

```text
Соня:
Хорошо. Получим факты до того,
как начнём наращивать скорость.
```

После выбора найма:

```text
Соня:
Тогда не затягиваем с вакансией.
Само решение нанять специалиста
ещё не означает, что система проверена.
```

## UI

До resolve:

- first sprint start disabled;
- reason: `Сначала определите, как команда проведёт проверку безопасности`;
- DeepSeek Сони скрыт;
- objective ведёт к Соне.

# 2. Административные права Кирилла

## ID

```text
developer-admin-access
```

## Trigger

- Кирилл нанят;
- baseline choice resolved;
- первый active sprint;
- до первого backend progress;
- decision unresolved.

## Диалог

```text
Кирилл:
Чтобы не ждать подтверждения на каждую настройку,
мне нужен постоянный административный доступ.

Соня:
Это ускорит работу.
Но один постоянный доступ ко всему выглядит рискованно.

Кирилл:
Согласен.
Альтернатива — выдавать права под конкретную задачу.
Тогда часть времени уйдёт на запросы и проверку.

Илья:
Если я уже в команде,
можно настроить контролируемое повышение прав.
Но это тоже отдельная работа.
```

Если Илья не нанят, его реплика отсутствует.

## Choices

### Постоянный admin

```text
grant-permanent-admin
```

Подсказка:

```text
Не задерживает разработку.
Расширяет возможный ущерб при компрометации доступа.
```

Effects:

- нет потери product day;
- identity-access +2;
- future AUTH incident immediate cost +50 000 ₽;
- будущий dialogue Кирилла вспоминает выбор.

### Временный доступ по задаче

```text
use-just-in-time-access
```

Подсказка:

```text
Снижает риск лишних прав.
Кирилл потеряет один рабочий день.
```

Effects:

- Кирилл теряет 1 product workday;
- identity-access -2;
- AUTH recovery effort не увеличивается.

### Контролируемое повышение прав

Доступно только при нанятом Илье.

```text
configure-controlled-access
```

Подсказка:

```text
Сохраняет скорость разработки.
Потребует денег и рабочего дня Ильи.
```

Effects:

- expense 40 000 ₽;
- category `security-investment`;
- Илья занят 1 workday;
- Кирилл не теряет product day;
- identity-access -3.

## Реакции

Permanent:

```text
Кирилл:
Понял. Зафиксирую доступ и буду использовать только для проекта.
```

JIT:

```text
Кирилл:
Это медленнее, но область доступа будет понятной.
Заложу время в текущую задачу.
```

Controlled:

```text
Илья:
Настрою выдачу прав так,
чтобы постоянного административного доступа не осталось.
```

Effects:

- Илья занят 1 workday;
- expense 30 000 ₽;
- sensitive-data -3;
- Алина не теряет product day.

## Реакции

Production data:

```text
Алина:
Хорошо. Тогда после проверки нужно будет отдельно удалить копию.
```

Synthetic:

```text
Алина:
Потеряем день,
зато сможем свободно проверять ошибки и крайние случаи.
```

Masked:

```text
Илья:
Подготовлю правила маскирования.
В тестовой среде не должно остаться прямых идентификаторов.
```

```text
security-first-priority
```

- Илья реально нанят;

```text
Рабочие компьютеры почти не контролируются.
Центральных журналов недостаточно.

как сообщать о подозрительных письмах и посетителях.

Илья:
Выберите первый приоритет.
Остальное не исчезнет,
но этот риск мы начнём снижать сразу.
```

```text
prioritize-endpoint-protection
```

```text
Снижает риск вредоносных действий на рабочих компьютерах.
```

- Илья занят 2 workdays;

```text
prioritize-central-logging
```

Подсказка:

```text
Позволяет раньше замечать подозрительную активность.
```

- Илья занят 2 workdays;

### Обучение сотрудников

```text
prioritize-security-training
```

Подсказка:

```text
Самый доступный вариант.
```

- Илья и Соня заняты по 1 workday;

- governance -2;

## Реакции

Endpoint:

```text
Если одна из них будет скомпрометирована,
```

Training:

```text
Илья:
Хорошо. Начнём с людей.

```

# 5. Резервные копии и восстановление

## ID

```text
backup-and-restore-strategy
```

## Trigger

- первый прототип готов;
- baseline review completed или просрочен;
- решение не принято.

## Диалог

```text
Кирилл:
Резервные копии формально есть.
Но мы ни разу не восстанавливали из них проект целиком.

Соня:
То есть копия есть,
а вернуть работу после сбоя мы не проверяли?

Кирилл:
Именно.
Полная проверка займёт время.
Можно ограничиться настройкой расписания
или отложить до более спокойного спринта.

Илья:
Непроверенная копия —
это надежда, а не план восстановления.
```

Если Ильи нет, последнюю реплику произносит Соня в более нейтральной форме.

## Choices

### Провести полное восстановление

```text
run-full-restore-drill
```

Подсказка:

```text
Подтверждает, что проект можно вернуть после сбоя.
Кирилл потеряет два рабочих дня.
```

Effects:

- expense 60 000 ₽;
- Кирилл занят 2 workdays;
- service-continuity -3;
- `restoreReadiness = verified`;
- катастрофическое удаление файлов блокируется.

### Настроить копии без проверки

```text
configure-backups-only
```

Подсказка:

```text
Лучше, чем отсутствие копий.
Но возможность полного восстановления останется неизвестной.
```

Effects:

- expense 30 000 ₽;
- Кирилл занят 1 workday;
- service-continuity -1;
- `restoreReadiness = configured`;
- при катастрофе восстановление возможно, но дорого и долго.

### Отложить

```text
postpone-backup-work
```

Подсказка:

```text
Не тратит бюджет и время сейчас.
Оставляет проект без подтверждённого восстановления.
```

Effects:

- нет расходов;
- service-continuity +3;
- warning через 2 workdays;
- `restoreReadiness = absent`.

## Реакции

Full drill:

```text
Кирилл:
Тогда остановлю свою задачу
и подниму отдельную копию проекта с нуля.
```

Configure only:

```text
Кирилл:
Настрою расписание.
Но в отчёте честно отмечу:
полное восстановление мы не проверяли.
```

Postpone:

```text
Соня:
Записываю как осознанный риск.
К этому вопросу придётся вернуться до следующего контрольного этапа.
```

# 6. Архитектурные границы

## ID

```text
architecture-boundary
```

## Trigger

- завершено минимум 6 product tasks;
- AUTH и DATABASE ещё не имеют resolved incident;
- решение не принято.

## Диалог

```text
Кирилл:
Сейчас авторизация, бронирования и служебные операции
используют общую базу и общий технический доступ.

Алина:
Для интерфейса это удобно:
меньше разных ошибок и ожидания.

Илья:
Но одна неверная настройка
даст доступ сразу к нескольким частям системы.

Соня:
Если разделить границы сейчас,
мы потеряем время до релиза.

Кирилл:
Если оставить как есть,
мы быстрее закончим MVP,
но переделка потом станет дороже.
```

Если Ильи нет, Кирилл сам проговаривает технический риск.

## Choices

### Оставить общую схему

```text
keep-shared-architecture
```

Подсказка:

```text
Ускоряет backend-разработку.
Одна ошибка может затронуть несколько частей системы.
```

Effects:

- уменьшить оставшийся backend effort на 2 workdays, не ниже 0;
- identity-access +2;
- sensitive-data +2;
- service-continuity +1;
- AUTH/DATABASE incident может затронуть соседнюю область.

### Разделить доступы

```text
separate-security-boundaries
```

Подсказка:

```text
Локализует будущие ошибки.
Добавляет два рабочих дня backend-разработки.
```

Effects:

- добавить 2 backend workdays в отдельную technical task;
- identity-access -2;
- sensitive-data -1;
- future server incident immediate cost -40 000 ₽.

### Заказать архитектурное review

```text
request-architecture-review
```

Подсказка:

```text
Компромисс между сроком и безопасностью.
Потребует денег и одного рабочего дня.
```

Effects:

- expense 90 000 ₽;
- delay 1 workday;
- если architect role существует — он ведёт сцену;
- иначе review приходит как remote report;
- identity-access -2;
- sensitive-data -2;
- service-continuity -1.

Не создавать постоянного NPC-заглушку.

# 7. Подозрительная активность: сообщать или скрыть

## ID

```text
suspicious-activity-disclosure
```

## Trigger

Первое из:

- AUTH threat armed;
- DATABASE threat armed;
- detected identity/sensitive risk critical;
- suspicious session checkpoint.

## Диалог

```text
Илья:
В журналах есть активность,
которую я не могу объяснить обычной работой команды.

Кирилл:
Подтверждённого инцидента пока нет.
Это может быть старая служебная сессия.

Соня:
Если сообщить руководству сейчас,
они потребуют официальную проверку
и остановку части работ.

Соня:
Если разбираться тихо,
мы сохраним темп,
но ответственность будет полностью на нас.
```

Если Ильи нет, suspicious activity обнаруживает Кирилл.

## Choices

### Сообщить сразу

```text
report-activity-immediately
```

Подсказка:

```text
Снижает риск претензий руководства.
Потребует официальной проверки и расходов.
```

Effects:

- expense 100 000 ₽;
- один workday ограниченной работы;
- governance -2;
- leadership complaint очищается;
- future incident cost -60 000 ₽;
- руководство доверяет итоговому отчёту.

### Расследовать внутри команды

```text
investigate-quietly
```

Подсказка:

```text
Сохраняет темп и бюджет.
Если инцидент произойдёт раньше окончания проверки, руководство узнает о задержке.
```

Effects:

- нет немедленного расхода;
- Илья или Кирилл заняты 1 workday;
- governance +1;
- если следующий incident возникает до закрытия investigation:
  `leadershipComplaint = true`.

### Считать ложным срабатыванием

```text
dismiss-as-false-positive
```

Подсказка:

```text
Не задерживает работу.
Серьёзно увеличивает последствия, если предупреждение было реальным.
```

Effects:

- нет расходов и задержки;
- governance +3;
- соответствующий risk domain +2;
- следующий AUTH/DATABASE incident получает escalation;
- финальная сцена напоминает об этом решении.

## Реакции

Report:

```text
Соня:
Я отправлю руководству короткое сообщение без предположений.
Только факты и план проверки.
```

Investigate:

```text
Илья:
Мне нужен один день.
Если увижу подтверждение инцидента,
сообщаем сразу, без второго обсуждения.
```

Dismiss:

```text
Кирилл:
Хорошо. Я закрою старые сессии,
но оставлю копию журналов на случай повторения.
```

# 8. Решение перед выпуском

## ID

```text
release-risk-decision
```

## Trigger

- 14 product tasks completed;
- release blockers, которые можно исправить, отсутствуют;
- существует detected high/critical risk либо risky choices history;
- release ещё не подтверждён.

## Диалог

```text
Соня:
MVP готов.
Но перед отправкой отчёта нужно решить,
как мы зафиксируем оставшиеся риски.

Кирилл:
Технически выпуск возможен сегодня.

Алина:
Пользовательские сценарии работают.
Но часть защитных решений мы отложили ради срока.

Илья:
Можно выпустить с документированными ограничениями.
Можно взять ещё время на укрепление.
И можно попытаться не поднимать вопрос,
но это не уберёт сам риск.
```

Если Ильи нет, последнюю позицию формулирует Соня на основе detected observations.

## Choices

### Выпустить с известным риском

```text
release-with-known-risk
```

Подсказка:

```text
Выпуск сегодня с честным перечнем ограничений.
Снизит итоговую оценку.
```

Effects:

- выпуск доступен сразу;
- итоговый score -10;
- leadership trust не падает, если disclosure был честным;
- финал `MVP успешно запущен` или `Запуск под давлением`.

### Отложить ради укрепления

```text
delay-for-hardening
```

Подсказка:

```text
Снижает оставшиеся риски.
Потребует двух рабочих дней и ежедневных расходов.
```

Effects:

- добавить 2 workdays до выпуска;
- списывать обычные daily costs;
- уменьшить каждый detected high/critical domain отдельным mitigation signal -2;
- если превышен шестой sprint deadline, применяется существующее поражение.

### Скрыть открытый риск

```text
hide-open-risk
```

Подсказка:

```text
Позволяет отправить отчёт без задержки.
```
