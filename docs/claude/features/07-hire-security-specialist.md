# Цель итерации

Реализовать ветку, в которой игрок одобрил штатного специалиста по безопасности.

Игрок должен:

1. открыть панель команды;
2. увидеть доступную вакансию специалиста;
3. ознакомиться с фиксированным кандидатом;
4. подтвердить найм;
5. увидеть нового сотрудника в составе команды;
6. увидеть его NPC на карте;
7. начать платить ему зарплату со следующего завершённого рабочего дня;
8. завершить задачу найма.

Ветка отказа не получает доступ к кандидату и продолжает игру без безопасника.

Feature 07 не добавляет повторные аудиты, штрафы, аудитные замечания и числовое снижение рисков. Это Feature 08.

# 1. Зафиксированный персонаж

В игре появляется один фиксированный сюжетный специалист.

## Илья Власов

```ts
{
  id: "ilya-vlasov",
  name: "Илья Власов",
  role: "security-specialist",
  roleLabel: "Специалист по информационной безопасности",
  dailySalary: 9_000,
}
```

Краткое описание для UI:

> Специалист по защите инфраструктуры и внутренних процессов. Помогает находить риски до того, как они превращаются в инциденты.

Persona:

> Спокойный, внимательный и прямолинейный. Не обещает абсолютной безопасности и всегда объясняет цену риска. Не любит временные решения, которые становятся постоянными.

## Почему один кандидат

В Feature 07 нет рынка кандидатов.

Причины:

- Илья является сюжетным персонажем;
- он будет участвовать в будущих аудитах и событиях;
- игрок уже принял стратегическое решение о наличии роли;
- сравнение случайных кандидатов не добавляет важного выбора на этом этапе.

Не добавляй:

- альтернативных безопасников;
- случайные характеристики;
- интервью;
- отказ кандидата;
- торг по зарплате.

# 3. Доступность кандидата

Илья доступен для найма только если:

```ts
staffingDecision === "approve-security-hire"
```

и одновременно:

```text
post-audit conversation completed
Илья ещё не нанят
игра не находится в review
не запущена cutscene
не открыта server minigame
не открыт другой blocking overlay
```

Создай чистое правило:

```ts
export type SecurityHireContext = {
  staffingDecision?: SecurityStaffingDecision;
  postAuditConversationStatus: PostAuditConversationStatus;
  isAlreadyHired: boolean;
  sprintPhase: SprintPhase;
  isCutsceneRunning: boolean;
  isServerMinigameOpen: boolean;
  isBlockingOverlayOpen: boolean;
};

export function canHireSecuritySpecialist(
  context: SecurityHireContext
): SecurityHireEligibility;
```

Рекомендуемый результат:

```ts
export type SecurityHireEligibility = {
  allowed: boolean;
  blockingReasons: SecurityHireBlockingReason[];
};
```

## Ветка отказа

При:

```ts
staffingDecision === "decline-security-hire"
```

панель команды:

- не показывает карточку кандидата;
- не показывает заблокированную кнопку;
- не предлагает пересмотреть решение;
- не показывает «скоро доступно».

Текущий состав остаётся:

```text
Соня
Кирилл
Алина
```

Задача `Закрыть замечания аудита силами команды` остаётся.

# 5. Подтверждение найма

После нажатия `Нанять` открой подтверждение.

```text
Нанять Илью Власова?

Роль: Специалист по информационной безопасности
Зарплата: 9 000 ₽ в день

Текущие расходы за день: 37 000 ₽
Расходы после найма: 46 000 ₽

Зарплата начнёт списываться при следующем завершении рабочего дня.
```

Кнопки:

- `Нанять`;
- `Отмена`.

## Отмена

После `Отмена`:

- hire record не создаётся;
- задача не завершается;
- бюджет не меняется;
- журнал не меняется;
- NPC не появляется;
- время не двигается.

## Подтверждение

После подтверждения:

- создаётся одна hire record;
- бюджет сразу не меняется;
- задача `hire-security-specialist` становится выполненной;
- NPC Ильи появляется в офисе;
- прогноз ежедневных расходов становится 46 000 ₽;
- зарплата попадёт в следующую ежедневную транзакцию.

Не блокируй найм из-за низкого бюджета.

Механика банкротства и game over ещё не реализована.

# 6. Use-case найма

Не вызывай generic `teamStore.hireEmployee()` напрямую из React-компонента.

Создай узкую операцию:

```ts
export function hireSecuritySpecialist(
  context: HireSecuritySpecialistContext
): HireSecuritySpecialistResult;
```

Она должна:

1. получить актуальный staffingDecision;
2. проверить completed post-audit conversation;
3. проверить eligibility;
4. проверить, что employee id существует;
5. создать hire record через team-store;
6. завершить department task;
7. вернуть структурированный результат;
8. не списывать деньги;
9. не двигать время.

Рекомендуемый результат:

```ts
export type HireSecuritySpecialistResult =
  | {
      hired: true;
      employeeId: "ilya-vlasov";
    }
  | {
      hired: false;
      reason:
        | "decision-not-approved"
        | "conversation-not-completed"
        | "already-hired"
        | "invalid-game-state"
        | "unknown-employee";
    };
```

Операция должна быть идемпотентной.

Повторный вызов:

```ts
{
  hired: false,
  reason: "already-hired"
}
```

не должен:

- дублировать hire record;
- повторно завершать task;
- дублировать NPC;
- дублировать зарплату.



- reload сохраняет done;
- reset удаляет или возвращает task согласно story flow;
- ветка отказа не создаёт эту task.

```text
Аренда офиса                         8 000 ₽
Серверы и сервисы                    4 000 ₽
Проджект-менеджер                    6 000 ₽
Административные расходы             2 000 ₽
Зарплата: Кирилл Морозов             9 000 ₽
Зарплата: Алина Белова               8 000 ₽
Итого                               37 000 ₽
```

## После найма

```text
Аренда офиса                         8 000 ₽
Серверы и сервисы                    4 000 ₽
Проджект-менеджер                    6 000 ₽
Административные расходы             2 000 ₽
Зарплата: Кирилл Морозов             9 000 ₽
Зарплата: Алина Белова               8 000 ₽
Зарплата: Илья Власов                9 000 ₽
Итого                               46 000 ₽
```

Полный спринт с Ильёй:

```text
460 000 ₽
```

## Правила

- зарплата Сони не дублируется;
- зарплата Ильи появляется только после hire record;
- день, завершённый до найма, не меняется задним числом;
- следующая ежедневная операция использует новый состав;
- одна ежедневная операция по-прежнему агрегирует все расходы;
- отдельная salary transaction для Ильи не создаётся;
- id ежедневной операции не меняется;
- идемпотентность Feature 02 сохраняется.

Добавь salary line:

```ts
{
  code: "salary:ilya-vlasov",
  title: "Зарплата: Илья Власов",
  amount: 9_000,
}
```

# 11. Модель персонажа

Используй существующий реальный ассет проекта.

Требования к ассету:

- отдельная модель офисного персонажа;
- не используется Соней, Кириллом или Алиной;
- совместима с текущими анимациями;
- визуально отличается от других постоянных NPC;
- не является кубом или временным примитивом.

Приоритет:

1. готовая модель, явно предназначенная для безопасника;
2. свободная совместимая модель офисного сотрудника;
3. отдельная мужская модель, не занятая другим persistent NPC.

Запрещено:

- копировать Кирилла как второго идентичного персонажа;
- использовать модель Сони;
- делать невидимого NPC;
- скачивать внешний ассет;
- заменять персонажа цилиндром или капсулой.

## Если ассета нет

Claude Code должен:

1. точно перечислить просмотренные каталоги;
2. указать, каких файлов не хватает;
3. указать ожидаемый формат модели и анимаций;
4. реализовать чистую игровую логику и UI, если это безопасно;
5. не считать Feature 07 полностью принятой;
6. не создавать визуальную заглушку.

# 12. Базовая автономная жизнь

Илья подключается к существующему planner.

Он может использовать существующие активности:

- `work`;
- `meeting`;
- `coffee`;
- `break`;
- `game`;
- `wander`.

Добавь одну минимальную role-specific активность:

```ts
"security-round"
```

или эквивалент текущего naming style.

## Security round

Это визуальный обход офиса.

Допустимые точки:

- серверная;
- Open Space рядом с рабочими местами;
- переговорная.

Поведение:

1. planner выбирает activity;
2. NPC идёт к одной допустимой точке;
3. некоторое время находится там;
4. возвращается к обычному planner;
5. корректно освобождает claims;
6. не запускает аудит;
7. не меняет числовые риски;
8. не чинит сервер автоматически.

Не создавать сложный маршрут из десятков обязательных точек.

## Рекомендуемые веса

```text
work            0.45
security-round  0.25
meeting         0.10
coffee          0.10
break/game      0.10
```

Используй существующий механизм нормализации весов.

Точные веса могут быть адаптированы, но `security-round` должна быть заметна при ручной проверке.

# 13. Взаимодействие с серверной

Илья может заходить в серверную только как визуальная активность.

Он не должен:

- автоматически открывать server minigame;
- автоматически ремонтировать стойки;
- менять incident history;
- сбрасывать failures;
- давать бесплатный ремонт;
- блокировать игроку доступ навсегда.

Если server room имеет access constraints, добавь Илью в допустимый NPC access list минимально.

Не меняй доступ игрока.
