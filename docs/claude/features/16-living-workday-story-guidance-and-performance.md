# Feature 16 — живой рабочий день, сюжетный ритм, подсказки и оптимизация

## Как использовать этот файл

Передай Claude Code только этот feature-файл вместе с доступом к актуальному репозиторию.

Постоянные правила проекта подключаются через:

- `CLAUDE.md`;
- `AGENTS.md`;
- `docs/claude/00-implementation-workflow.md`;
- `docs/claude/00-fixed-game-rules.md`;
- актуальные документы из `docs/qa/`.

Feature 01–15 считаются реализованными и принятыми.

Эта итерация меняет игровой ритм и удобство прохождения, но не добавляет новую ветку кампании, новых сотрудников, новые условия победы или поражения.

---

# Проблема

Текущий игровой цикл ощущается слишком механическим:

1. игрок планирует спринт;
2. после этого в офисе почти ничего заметного не происходит;
3. основной способ продвижения — многократно нажимать `Завершить день`;
4. сюжетные разговоры плохо заметны или не запускаются;
5. над NPC есть иконки чата, но игрок не понимает, где обычная беседа, а где обязательный сюжет;
6. отсутствует ясный ответ на вопрос «что мне делать сейчас?»;
7. события и результаты существуют в stores, но слабо представлены в самой 3D-сцене;
8. игра подлагивает, особенно при движении по офису и работе нескольких NPC.

Feature 16 должна исправить именно эти проблемы.

---

# Главная цель

После планирования спринта игра должна ощущаться как живой рабочий день:

```text
планирование
→ короткий командный kickoff
→ понятная текущая цель
→ работа NPC и реакция офиса
→ сюжетное или управленческое событие
→ автоматическое завершение дня
→ понятный ежедневный итог
→ следующий день
```

Игрок больше не должен продвигать кампанию только повторным нажатием одной кнопки.

---

# Ключевое изменение правила времени

Feature 16 заменяет прежнее правило ручного завершения дня.

## Было

```text
Игрок нажимает «Завершить день»
→ вызывается completeWorkday
```

## Становится

```text
Игрок выполняет обязательные действия текущего дня
→ Workday Flow достигает ready-to-complete
→ игра автоматически запускает completeWorkday
→ показывается daily report
```

Игровое время всё ещё:

- не зависит от реальных часов;
- не продвигается при обычной ходьбе;
- не продвигается от ожидания;
- не продвигается от необязательного разговора;
- не продвигается в фоне;
- не использует браузерный таймер как источник времени.

День завершается автоматически только после выполнения детерминированных условий игрового дня.

# 1. Новый Workday Flow

Создай отдельный небольшой Zustand-store.

Рекомендуемое имя:

`src/game/workdayFlowStore.ts`

## Состояния

```ts
export type WorkdayFlowPhase =
  | "idle"
  | "morning-briefing"
  | "active"
  | "ready-to-complete"
  | "completing"
  | "daily-report"
  | "waiting-for-events";

export type WorkdayObjectiveKind =
  | "talk-to-npc"
  | "open-whiteboard"
  | "review-team-status"
  | "resolve-story-dialogue"
  | "inspect-server"
  | "assign-security-work"
  | "review-risk"
  | "wait-for-team-beat";

export type WorkdayObjective = {
  id: string;
  kind: WorkdayObjectiveKind;
  title: string;
  description: string;
  targetNpcId?: string;
  targetObjectId?: string;
  completed: boolean;
  optional: boolean;
};

export type WorkdayBeatId =
  | "sprint-kickoff"
  | "daily-team-checkin"
  | "mid-sprint-status"
  | "pre-review-status"
  | "security-followup"
  | "budget-warning"
  | "server-recovery-status"
  | "risk-observation"
  | "quiet-workday";

export type WorkdayFlowState = {
  sprintNumber: number;
  day: number;
  phase: WorkdayFlowPhase;
  objectives: WorkdayObjective[];
  selectedBeatId?: WorkdayBeatId;
  morningBriefingCompleted: boolean;
  teamBeatCompleted: boolean;
  autoCompletionRequested: boolean;
  completionStarted: boolean;
  lastCompletedWorkdayId?: string;
};
```

Названия можно адаптировать к текущему стилю проекта.

Не создавай универсальный event engine. Workday Flow управляет только ритмом одного игрового дня.

# 2. Инициализация дня

Новый день начинается:

- после старта спринта;
- после закрытия daily report предыдущего дня;
- после sprint review и запуска следующего спринта;
- после восстановления сохранения в active phase.

При инициализации:

1. прочитать актуальное состояние игры;
2. выбрать один обязательный beat по фиксированному приоритету;
3. создать 1–3 понятных objectives;
4. установить phase;
5. обновить HUD;
6. не двигать игровое время.

Инициализация идемпотентна для:

```text
sprint-{sprintNumber}:day-{day}
```

Reload не должен создавать новый набор целей или повторно запускать завершённый сюжетный beat.

---

# 3. День после планирования спринта

После нажатия `Начать спринт` не должен сразу появляться обычный пустой active-state.

Сначала запускается обязательный kickoff.

## Первый день спринта

```text
phase = morning-briefing
beat = sprint-kickoff
```

HUD:

```text
Текущая цель

Проведите короткий kickoff с командой
у доски планирования.
```

На whiteboard появляется сюжетный marker.

Соня, Кирилл и Алина:

- получают цель подойти к whiteboard;
- используют существующую навигацию;
- не телепортируются;
- корректно освобождают прежние claims;
- собираются рядом без наложения друг на друга.

Илья участвует только при реальном найме.

---


# 3.1. Блокировка планирования до найма разработчиков

Игрок не может добавлять продуктовые задачи в план спринта, пока не наняты оба разработчика:

- Кирилл Морозов;
- Алина Белова.

Проверка должна выполняться не только при старте спринта, но и при любой попытке:

- добавить задачу в очередь Кирилла;
- добавить задачу в очередь Алины;
- переместить задачу в sprint plan;
- восстановить некорректный draft после reload;
- вызвать соответствующий use-case напрямую.

## UI до найма разработчиков

Product backlog можно просматривать, но действия планирования недоступны.

Вместо обычного пустого планирования показывай:

```text
Сначала соберите команду разработки

Чтобы планировать задачи OfficeFlow, наймите:
• backend-разработчика Кирилла Морозова;
• frontend-разработчика Алину Белову.
```

Кнопки добавления задачи:

- disabled;
- имеют понятную причину;
- не создают скрытый draft;
- не изменяют порядок очередей.

Добавь кнопку:

```text
Перейти к найму
```

Она:

- закрывает или переводит whiteboard на нужную секцию;
- подсвечивает панель команды или точку найма;
- не нанимает сотрудников автоматически;
- не телепортирует игрока.

## Сюжетная подсказка Сони

При первой попытке открыть планирование без разработчиков запускается короткий обязательный диалог с Соней.

Marker должен быть сюжетным, а не DeepSeek-чатом.

```text
Соня:
Пока нам некому выполнять задачи OfficeFlow.

Соня:
Сначала наймите backend- и frontend-разработчика.
После этого мы сможем распределить задачи по спринту.
```

После разговора появляется objective:

```text
Наймите Кирилла и Алину
```

Objective считается выполненным только после двух реальных hire records.

Не повторяй обязательный диалог при каждом открытии доски. После первого раза оставляй понятную статическую подсказку.

## Чистая логика

Добавь или расширь:

```ts
export function canPlanProductSprint(
  hires: HireRecord[]
): ProductPlanningEligibility;
```

Ожидаемые причины:

```ts
type ProductPlanningBlockingReason =
  | "backend-developer-not-hired"
  | "frontend-developer-not-hired";
```

Generic store action не должна позволять обойти это правило.

## Миграция повреждённого draft

Если в сохранении есть planned product tasks, но один или оба разработчика не наняты:

- не создавать фиктивные hire records;
- удалить только недопустимые sprint assignments;
- сохранить product backlog;
- сохранить прогресс уже завершённых задач;
- показать objective найма;
- не сбрасывать остальные stores.

# 4. Сюжетная сцена kickoff

Добавь короткую обязательную сцену:

```text
sprint-kickoff
```

Она запускается, когда:

- sprint active;
- day 1;
- игрок подошёл к whiteboard;
- команда достигла допустимых meeting positions;
- нет другого blocking event.

## Базовые реплики

Соня:

```text
План на спринт готов.
Давайте быстро сверим приоритеты и риски.
```

Кирилл сообщает:

- свою первую backend-задачу;
- суммарную нагрузку;
- перегрузку, если planned load > 10.

Алина сообщает:

- свою первую frontend-задачу;
- суммарную нагрузку;
- перегрузку, если planned load > 10.

Илья, если нанят, сообщает одно из:

- активное замечание;
- высокий обнаруженный риск;
- отсутствие срочных проблем.

Соня завершает:

```text
Хорошо. Начинаем работу.
Если появится блокер, я отмечу его в текущих целях.
```

## Требования

- реплики строятся из настоящего sprint plan;
- internal ids не показываются;
- DeepSeek не используется для обязательной сцены;
- сцена проходит один раз на спринт;
- после reload не повторяется, если уже завершена;
- после сцены phase становится `active`.

# 5. Ежедневные beats

Каждый день должен иметь один заметный beat.

Это не обязательно кат-сцена.

Допустимые формы:

- короткий обязательный диалог;
- NPC–NPC разговор с субтитрами;
- визуальная реакция команды;
- короткий status-card;
- уведомление с необходимым действием;
- спокойный рабочий день с наблюдаемой работой NPC.

## Приоритет выбора

Используй первый подходящий beat:

1. обязательный сюжетный диалог;
2. pending управленческое действие;
3. предупреждение о критическом бюджете;
4. активное восстановление сервера;
5. новое обнаруженное наблюдение риска;
6. mid-sprint status;
7. pre-review status;
8. daily team check-in;
9. quiet workday.

Не выбирай случайно.

Не создавай новый beat после каждого render.

---

# 6. Mid-sprint status

В день 5 каждого спринта:

```text
beat = mid-sprint-status
```

Игрок получает objective:

```text
Поговорите с Соней о ходе спринта.
```

Соня сообщает:

- сколько задач завершено;
- какие задачи в работе;
- перегружен ли кто-то;
- сколько бюджета осталось;
- есть ли security blocker;
- прогноз завершения спринта.

Пример:

```text
Соня:
Мы завершили четыре задачи из семи запланированных.

Кирилл сейчас отвлечён на восстановление AUTH,
поэтому его backend-задача отстаёт на один день.

По бюджету запас есть, но ещё один штраф
сильно сократит пространство для ошибок.
```

После диалога день не завершается немедленно, если остаётся другое обязательное действие.

---

# 7. Pre-review status

В день 9:

```text
beat = pre-review-status
```

Цель:

```text
Проверьте готовность спринта вместе с командой.
```

Разговор показывает:

- что точно завершится;
- что не успевает;
- незакрытые security work;
- активный простой;
- риск дедлайна;
- прогноз расходов следующего дня.

Это должно помогать игроку понимать последствия до review.

# 8. NPC–NPC разговоры

Добавь короткие наблюдаемые разговоры между персонажами.

Они не требуют участия игрока и не блокируют управление.

## Примеры ситуаций

### Кирилл и Алина

Когда их задачи относятся к одному feature:

```text
Алина:
Мне нужен точный формат ответа для формы бронирования.

Кирилл:
После обеда зафиксирую контракт.
Не начинай обработку ошибок по старому варианту.
```

### Соня и Кирилл

При перегрузке:

```text
Соня:
У тебя снова больше десяти дней работы.

Кирилл:
Да. Если не отвлекусь на инфраструктуру,
основную часть успею, но запас почти нулевой.
```

### Соня и Илья

При detected high risk:

```text
Соня:
Насколько срочно нужно переключать команду?

Илья:
Инцидента ещё нет.
Но откладывать исправление дальше уже опасно.
```

### Кирилл и Илья

При server recovery:

```text
Илья:
Я собрал журналы до сбоя.

Кирилл:
Хорошо. Тогда я не буду повторно искать точку отказа.
```

## Правила

- максимум один такой разговор за день;
- реплики выбираются детерминированно;
- разговор происходит только у допустимых meeting points;
- NPC не телепортируются;
- subtitle виден игроку в разумном радиусе;
- если игрок далеко, HUD показывает короткую запись: `Команда обсудила текущий блокер`;
- разговор не двигает время;
- разговор не заменяет обязательные сюжетные диалоги;
- DeepSeek может использоваться только как необязательная вариация;
- всегда существует статический fallback.

# 9. Иконки над NPC

Раздели визуальные состояния.

## Обязательный сюжетный разговор

Используй заметный marker:

```text
!
```

или отдельную принятую иконку задачи.

Цвет должен отличаться от обычного чата.

## Необязательный свободный разговор

Используй существующую иконку чата.

Она не должна постоянно висеть над всеми персонажами.

Показывай её:

- при наведении;
- при приближении;
- когда у NPC есть новый contextual response;
- когда игрок выбрал режим общения.

## NPC–NPC разговор

Показывай компактные speech bubbles над участниками только во время разговора.

Игрок должен визуально отличать:

- обязательный сюжет;
- текущую цель;
- необязательный разговор;
- автоматический разговор NPC.

---


## Подписи персонажей

Над постоянными NPC должна отображаться аккуратная читаемая подпись:

```text
Соня Соколова
Проджект-менеджер
```

```text
Кирилл Морозов
Backend-разработчик
```

```text
Алина Белова
Frontend-разработчик
```

```text
Илья Власов
Специалист по информационной безопасности
```

Требования:

- имя и должность визуально разделены;
- должность меньше имени, но остаётся читаемой;
- не показывать internal role ids;
- подпись не должна закрывать лицо;
- подпись не должна перекрывать marker;
- размер не должен чрезмерно меняться при движении камеры;
- на большой дистанции подпись скрывается;
- сквозь стены подпись не отображается;
- подпись не перехватывает клики по сцене;
- HTML overlay не должен обновляться каждый frame без необходимости;
- оформление едино для всех постоянных NPC.

## Явное различие сюжетного разговора и DeepSeek

Игрок должен мгновенно понимать тип взаимодействия.

### Обязательный сюжетный разговор

Используй:

- заметный `!`;
- отдельный цвет;
- подпись `Сюжет`;
- objective в HUD;
- приоритет над любым другим разговором.

Пример tooltip:

```text
Сюжетный разговор
Обсудить результаты аудита
```

### Свободный DeepSeek-разговор

Используй отдельную иконку сообщения, например speech bubble со sparkle.

Пример tooltip:

```text
Поговорить
Свободный разговор
```

DeepSeek-иконка:

- не должна выглядеть как обязательная задача;
- не должна постоянно висеть над всеми NPC;
- появляется при приближении, наведении или новом контексте;
- скрывается, если у NPC есть обязательный сюжетный разговор;
- не перехватывает обязательный dialogue route.

### NPC–NPC разговор

Использует временные speech bubbles только во время реплик.

Не показывай постоянную интерактивную chat-иконку для автоматического разговора NPC.

## Приоритет interaction

При клике на NPC:

1. обязательный сюжетный разговор;
2. обязательное управленческое взаимодействие;
3. статический contextual dialogue;
4. свободный DeepSeek-чат.

Нельзя открыть DeepSeek вместо незавершённого сюжетного разговора.

# 10. Система текущей цели

Добавь постоянный, но компактный HUD-блок:

```text
Текущая цель
```

Он показывает только одно главное действие.

Примеры:

```text
Проведите kickoff у доски.
```

```text
Поговорите с Соней о результатах аудита.
```

```text
Назначьте исполнителя на восстановление AUTH.
```

```text
Проверьте новое наблюдение на вкладке «Безопасность».
```

```text
Команда работает. Наблюдайте за ходом дня.
```

Дополнительно:

- короткое объяснение, зачем это нужно;
- расстояние или направление до цели, если это объект/NPC;
- marker на объекте;
- кнопка `Показать`, которая кратко подсвечивает цель;
- не телепортировать игрока;
- не открывать panel автоматически без необходимости.

# 11. Контекстные подсказки

Если игрок не продвигается, показывай подсказки.

Реальный таймер допустим только для UI-подсказки. Он не влияет на игровой день.

## Уровни

### Через 20 секунд без прогресса

```text
Подсказка:
Текущая цель отмечена жёлтым маркером.
```

### Через 45 секунд

```text
Подсказка:
Подойдите к Соне и нажмите кнопку взаимодействия.
```

### Через 90 секунд

Показать кнопку:

```text
Показать цель
```

Она:

- поворачивает camera indicator;
- кратко подсвечивает target;
- не телепортирует;
- не завершает действие автоматически.

После любого реального прогресса таймер подсказок сбрасывается.

# 12. Условия автоматического завершения дня

Создай чистую функцию:

```ts
export function canAutoCompleteWorkday(
  context: AutoCompleteWorkdayContext
): AutoCompleteWorkdayEligibility;
```

День можно завершить автоматически, когда:

- sprint phase `active`;
- Workday Flow phase `active` или `ready-to-complete`;
- обязательный morning briefing завершён, если он был;
- обязательный beat завершён;
- все обязательные objectives completed;
- нет blocking dialogue;
- нет daily report;
- нет cutscene;
- нет server minigame;
- нет pending/running audit;
- нет pending/running intrusion;
- нет pending/running server incident;
- outcome не terminal;
- completion ещё не запускался для этого дня.

## Автоматический переход

После выполнения последней обязательной цели:

1. показать короткий status: `Рабочий день завершается`;
2. дать NPC закончить текущую короткую анимацию;
3. вызвать существующий `completeWorkday`;
4. открыть daily report;
5. не требовать клика `Завершить день`.

Допустима короткая UI-задержка до 1.5 секунд только для визуального перехода.

Она не является источником игрового времени.

# 13. Что происходит в quiet workday

Даже если нет сюжетного события, день не должен ощущаться пустым.

## Обязательное поведение

- NPC переходят к связанным рабочим местам;
- над активной задачей кратко показывается status;
- один NPC может сделать contextual comment;
- HUD показывает, над чем работает команда;
- после короткого наблюдаемого рабочего beat день завершается автоматически.

Пример HUD:

```text
Команда работает

Кирилл — API бронирований
Алина — форма бронирования
Илья — проверка прав доступа
```

Не требуй от игрока бессмысленно обходить каждого NPC.

Quiet beat должен завершаться после того, как:

- NPC достигли рабочих зон;
- прошёл короткий визуальный рабочий отрезок;
- нет блокеров.

Для завершения quiet beat допустим UI/gameplay timer 8–15 секунд.

Этот timer не является календарным временем и не должен работать при:

- pause;
- открытом меню;
- dialogue;
- скрытой вкладке;
- blocking overlay.

# 18. Reload и миграция

После reload необходимо восстанавливать:

- текущий beat;
- objectives;
- completed flags;
- phase;
- факт завершённого kickoff;
- факт завершённого mid-sprint/pre-review dialogue;
- completionStarted;
- current workday id.

## Нормализация

### `completing` после reload

Если financial/product/security side effects ещё не применены:

- вернуть `ready-to-complete`;
- безопасно повторить единый use-case.

Если workday transaction уже существует:

- не применять день повторно;
- перейти к daily report или waiting-for-events.

### `morning-briefing`

- восстановить objective;
- не дублировать NPC;
- не запускать вторую сцену.

### quiet beat timer

- можно начать короткий визуальный отрезок заново;
- день не должен примениться дважды.

Для старого сохранения Feature 15:

- active sprint получает новый Workday Flow для текущего дня;
- прошлые дни не переигрываются;
- kickoff не запускается задним числом, если current day > 1;
- day 5/day 9 beat можно создать только для текущего дня;
- другие stores не сбрасываются.

# 18.1. Кресло руководителя

Кресло CEO/руководителя является player-only объектом.

Ни один NPC не должен:

- выбирать его как рабочее место;
- получать claim на это кресло;
- использовать его в idle/activity planner;
- садиться туда после reload;
- занимать его во время кат-сцены, если сцена явно не требует обратного.

Добавь явное ограничение в catalog/claim rules:

```ts
occupancy: "player-only"
```

или эквивалент текущей архитектуры.

Не решай проблему только уменьшением веса activity.

## Посадка игрока

Текущие поддерживаемые модели игрока плохо совмещаются с креслом руководителя.

Исправь seated pose:

- положение таза относительно сиденья;
- высоту модели;
- поворот корпуса;
- положение ног;
- отсутствие пересечения со спинкой и столом;
- направление взгляда;
- плавный переход sit/stand;
- возврат управления после вставания.

Если доступны разные модели игрока, проверь каждую реально поддерживаемую модель.

Не меняй размеры самого персонажа только ради кресла.

Используй отдельный seat anchor/offset для CEO chair.

## Проверки

- только игрок может получить seat claim;
- NPC planner игнорирует chair;
- reload не помещает NPC в кресло;
- reset сохраняет player-only правило;
- игрок сидит без заметного clipping;
- камера не входит в голову или спинку кресла;
- вставание не помещает игрока внутрь стола.

# 18.2. Ускорение сцены незаблокированного экрана

В существующей сцене `security-breach` временные модели охраны/проверяющих слишком долго появляются и идут к кабинету руководителя.

Не создавай новую сцену. Оптимизируй существующую постановку.

## Целевой ритм

После trigger:

- первые временные актёры видимы не позднее чем через 1 секунду;
- движение начинается без длинной паузы;
- скорость cutscene actors выше обычной скорости офисных NPC;
- вся группа оказывается в кабинете руководителя примерно за 4–6 секунд;
- между прибытием и первой репликой нет лишней паузы;
- камера не ждёт пустой коридор.

Допустимо:

- выбрать spawn ближе к входу;
- использовать отдельную скорость движения cutscene actors;
- сократить лишние waypoints;
- синхронизировать actors не по самому медленному участнику;
- начинать реплики после прибытия ключевого actor, если остальные уже визуально рядом.

Нельзя:

- заметно телепортировать actor в поле зрения;
- пропускать обязательные реплики;
- ломать navmesh;
- оставлять actor после завершения сцены.

Добавь timeout/fallback:

- если actor не достиг позиции за разумный срок, безопасно перевести его на ближайшую допустимую cutscene position;
- fallback не должен зависать и не должен дублировать actor.

# 18.3. Гарантированно достижимая сцена проникновения без СКУД

Ветка без установленной СКУД должна реально приводить к сцене `office-intrusion` в обычном прохождении, если игрок игнорирует проблему и не снижает риск.

Проверь текущие условия Feature 09–10. Нельзя оставлять скрытую комбинацию, при которой игрок:

- получил предложение СКУД;
- не установил её;
- продолжил завершать дни;
- не выполнял mitigation;
- но угроза никогда не достигает pending.

## Нормальный пользовательский путь

Следующий сценарий должен быть детерминированно достижим:

```text
обнаружен office-access risk
→ предложение СКУД доступно
→ игрок откладывает или игнорирует внедрение
→ не закрывает связанные меры
→ проходит ограниченное число рабочих дней
→ угроза вооружается
→ показывается предупреждение
→ после срока запускается office-intrusion
```

## Эскалация отсутствия СКУД

Если:

- proposal status `available` или `postponed`;
- СКУД не `approved`, не `in-progress` и не `active`;
- detected office-access не ниже `elevated`;
- прошло 2 завершённых рабочих дня после предложения;
- игрок не снизил actual office-access ниже `elevated`;

добавь один раз:

```ts
{
  id: "access-control:not-implemented-in-time:office-access",
  domain: "office-access",
  impact: 2,
  source: "access-control-decision",
  sourceRef: "access-control-not-implemented-in-time",
}
```

Это должно сделать ветку игнорирования достаточно рискованной для существующего high-risk trigger.

Signal:

- создаётся один раз;
- не создаётся, если СКУД уже approved/in-progress/active;
- не создаётся, если игрок реально снизил риск;
- сохраняется после reload;
- удаляется общим reset;
- не заменяет исходные risk signals.

## Понятное предупреждение

Когда threat становится armed, HUD показывает:

```text
Риск проникновения

Контроль доступа не внедрён.
Устраните риск или запустите СКУД до истечения срока.
```

Покажи число оставшихся рабочих дней без raw risk score.

Предупреждение не раскрывает скрытую формулу, но объясняет причинно-следственную связь.

## Trigger

Проверь:

- due рассчитывается один раз;
- automatic Workday Flow не пропускает проверку;
- daily report имеет приоритет;
- audit имеет приоритет;
- сцена запускается после освобождения UI;
- reload `running -> pending`;
- отсутствие СКУД не ошибочно переводит status в `prevented`;
- scene effects применяются один раз;
- после resolved сцена не повторяется.

Добавь dev-only сценарий/fixture для быстрого воспроизведения, но не заменяй им нормальную игровую достижимость.

# 26. Ручная приёмка

## Сценарий 1. После планирования

1. Запланировать спринт.
2. Нажать `Начать спринт`.
3. Убедиться, что игра не переходит в пустой active-state.
4. Увидеть objective kickoff.
5. Подойти к whiteboard.
6. Увидеть сбор команды.
7. Прослушать реплики по реальному плану.
8. Убедиться, что команда расходится работать.

## Сценарий 2. Обычный день

1. Закрыть daily report.
2. Увидеть новую текущую цель.
3. Наблюдать работу NPC.
4. Увидеть короткий status или ambient dialogue.
5. Не нажимать кнопку завершения дня.
6. Убедиться, что день завершается автоматически.

## Сценарий 3. Обязательный диалог

1. Получить story objective.
2. Убедиться, что над NPC `!`, а не обычный chat.
3. Не подходить к NPC.
4. Убедиться, что день не завершается.
5. Дождаться подсказок.
6. Нажать `Показать цель`.
7. Подойти и завершить диалог.
8. Убедиться, что flow продолжился.

## Сценарий 4. NPC–NPC

1. Создать перегруженный sprint или security blocker.
2. Увидеть разговор персонажей.
3. Убедиться, что они подходят друг к другу.
4. Убедиться, что subtitle читается.
5. Убедиться, что после разговора они продолжают planner.
6. Убедиться, что разговор не повторяется в тот же день.

## Сценарий 5. Mid-sprint

1. Дойти до day 5.
2. Поговорить с Соней.
3. Проверить реальные данные прогресса и бюджета.
4. Убедиться, что устаревшие значения не показываются.

## Сценарий 6. Pre-review

1. Дойти до day 9.
2. Проверить прогноз незавершённых задач.
3. Проверить server/security blockers.
4. Проверить прогноз расходов day 10.

## Сценарий 7. Приоритеты

1. Сделать audit due.
2. Завершить objectives дня.
3. Убедиться, что day завершается автоматически.
4. Проверить daily report → audit → остальные события → review → новый flow.

## Сценарий 8. Производительность

1. Измерить baseline.
2. Играть минимум 20 минут.
3. Пройти Open Space, whiteboard, вход и серверную.
4. Запустить несколько NPC-dialogues.
5. Открывать панели.
6. Проверить FPS, draw calls, memory.
7. Повторить после оптимизаций.
8. Зафиксировать результат.

---


## Сценарий 9. Планирование до найма

1. Начать новую игру.
2. Не нанимать разработчиков.
3. Открыть product backlog.
4. Убедиться, что backlog виден, но добавить задачу нельзя.
5. Увидеть понятную причину.
6. Получить один обязательный разговор с Соней.
7. Нанять только Кирилла.
8. Убедиться, что planning всё ещё заблокирован.
9. Нанять Алину.
10. Убедиться, что planning разблокирован.

## Сценарий 10. Подписи и иконки NPC

1. Подойти к каждому постоянному NPC.
2. Проверить имя и должность.
3. Убедиться, что подписи не закрывают лица.
4. Отойти — подписи должны скрыться.
5. Получить обязательный сюжетный разговор.
6. Проверить отдельный `!` и tooltip `Сюжетный разговор`.
7. Убедиться, что DeepSeek-иконка скрыта.
8. Завершить сюжет.
9. Проверить доступность отдельной иконки свободного разговора.

## Сценарий 11. Кресло руководителя

1. Наблюдать за NPC не менее нескольких рабочих beats.
2. Убедиться, что никто не занимает кресло CEO.
3. Сесть игроком.
4. Проверить положение тела, ног и камеры.
5. Встать.
6. Убедиться, что игрок не застрял в столе.
7. Перезагрузить страницу.
8. Убедиться, что кресло остаётся player-only.

## Сценарий 12. Темп security-breach

1. Запустить обычный trigger `security-breach`.
2. Засечь момент появления временных actors.
3. Убедиться, что они появляются почти сразу.
4. Убедиться, что движение начинается без длинного ожидания.
5. Убедиться, что ключевые actors прибывают в кабинет примерно за 4–6 секунд.
6. Проверить начало реплик без пустой паузы.
7. Убедиться, что после сцены actors удалены.

## Сценарий 13. Проникновение без СКУД

1. Получить предложение СКУД.
2. Отложить его или не запускать внедрение.
3. Не выполнять связанные mitigation.
4. Завершить два рабочих дня.
5. Убедиться, что появилось предупреждение об усилении риска.
6. Убедиться, что threat armed и показан срок.
7. Продолжить игру до due.
8. Проверить порядок daily report и других событий.
9. Убедиться, что `office-intrusion` реально запускается.
10. Перезагрузиться перед сценой и проверить сохранение pending.
11. Завершить сцену и убедиться, что она не повторяется.

# 28. Критерии готовности

Feature 16 считается завершённой только если:

- production UI больше не требует ручного `Завершить день`;
- после планирования запускается kickoff;
- каждый день имеет заметный beat;
- существуют NPC–NPC разговоры;
- обязательный сюжет визуально отличается от optional chat;
- HUD всегда показывает актуальную цель;
- подсказки помогают найти действие;
- день автоматически завершается после mandatory objectives;
- quiet day не требует бессмысленного действия;
- daily report объясняет причины;
- следующий день сразу получает objective;
- event priority не сломан;
- reload не дублирует день или сцену;
- migration Feature 15 работает;
- manual End Day остаётся только dev-инструментом;
- performance baseline зафиксирован;
- bottlenecks исправлены на основе профилирования;
- результат до/после задокументирован;
- NPC и 3D-сцена не имеют накопительных утечек;
- задачи нельзя добавить в спринт до найма Кирилла и Алины;
- игрок получает понятный диалог и objective найма разработчиков;
- подписи имён и должностей читаемы и не содержат internal ids;
- сюжетный разговор визуально и функционально отличается от DeepSeek-чата;
- кресло руководителя доступно только игроку;
- посадка поддерживаемых моделей игрока в кресло не имеет заметного clipping;
- временные actors `security-breach` появляются и прибывают без долгого ожидания;
- ветка без СКУД и без mitigation детерминированно достигает `office-intrusion`;
- предупреждение о приближении проникновения понятно игроку;
- тесты проходят;
- E2E проходят;
- production build проходит.
