# Feature 03 — состав команды и найм первых разработчиков

## Как использовать этот файл

Передай Claude Code только этот feature-файл вместе с доступом к актуальному репозиторию.

Постоянные правила должны подключаться через корневой `CLAUDE.md`:

- `AGENTS.md`;
- `docs/claude/00-implementation-workflow.md`;
- `docs/claude/00-fixed-game-rules.md`.

Не передавай Claude Code инструкции Feature 04 и следующих этапов.

---

## Предварительные условия

Feature 01 и Feature 02 завершены и приняты.

В проекте уже работают:

- спринты по 10 условных дней;
- фазы `planning`, `active`, `review`;
- ручное завершение дня;
- стартовый бюджет 2 500 000 ₽;
- финансовый журнал;
- базовые расходы 20 000 ₽ в день;
- списание денег только при подтверждении дня;
- финансовая панель и итог спринта;
- сохранение и общий reset через `?intro`.

Если фактические имена файлов и функций отличаются, используй существующую реализацию. Не создавай копии store или логики предыдущих фич.

# Цель итерации

Добавить первый управляемый состав команды:

- Соня уже работает проджект-менеджером;
- игрок нанимает backend-разработчика Кирилла Морозова;
- игрок нанимает frontend-разработчика Алину Белову;
- нанятые сотрудники появляются в офисе;
- они используют существующую навигацию, state machine, claims и автономный planner;
- их зарплаты увеличивают расходы следующего завершаемого дня;
- состав команды сохраняется;
- первый спринт нельзя начать до найма обоих;
- задача `Сформировать команду` завершается после найма обоих.

На этой итерации разработчики ещё не выполняют продуктовые задачи и не создают прогресс OfficeFlow. Это Feature 04.

- сохранение хранит только факты найма;
- не дублировать model/animation-конфигурацию, если в проекте уже есть единый character roster.

# 3. Team store

Создай отдельный Zustand-store, например:

`src/game/teamStore.ts`

```ts
export type HireRecord = {
  employeeId: string;
  hiredAtSprint: number;
  hiredAtDay: number;
};

export type HireEmployeeResult =
  | { hired: true; employeeId: string }
  | {
      hired: false;
      reason:
        | "already-hired"
        | "unknown-employee"
        | "invalid-game-state";
    };

export type TeamState = {
  hires: HireRecord[];

  hireEmployee(
    employeeId: string,
    context: {
      sprintNumber: number;
      day: number;
    }
  ): HireEmployeeResult;

  resetTeam(): void;
};
```

Правила:

- новая игра: `hires = []`;
- Соня не хранится как hire record;
- Кирилл и Алина нанимаются независимо;
- повторный найм запрещён;
- неизвестный id запрещён;
- зарплата не списывается при клике `Нанять`;
- сотрудник входит в расходы при следующем подтверждении рабочего дня;
- наём не двигает время;
- наём не создаёт прогресс продукта;
- увольнения в этой фиче нет.

Не добавлять усталость, мораль, навыки, уровни, производительность, отпуск или испытательный срок.

# 4. Доступность найма

Панель команды доступна после завершения знакомства с Соней.

Наём разрешён, когда:

- пролог принят;
- завершён вступительный диалог Сони;
- игра находится в офисной фазе;
- не идёт кат-сцена;
- не открыта мини-игра;
- не открыт другой блокирующий оверлей.

Наём разрешён в `planning` и `active`.

В `review` изменение состава запрещено с сообщением:

> Завершите итоги спринта перед изменением состава команды.

Разрешение найма в `active` нужно для поддержки старых сохранений Feature 02.

# 7. Подтверждение найма

После `Нанять` открой подтверждение.

Пример Кирилла:

```text
Нанять Кирилла Морозова?

Роль: Backend-разработчик
Зарплата: 9 000 ₽ в день

Текущие расходы за день: 20 000 ₽
Расходы после найма: 29 000 ₽

Деньги начнут списываться при следующем завершении рабочего дня.

[Нанять] [Отмена]
```

После отмены ничего не меняется.

После подтверждения:

- создаётся одна hire record;
- бюджет сразу не меняется;
- обновляется прогноз расходов;
- карточка становится `В команде`;
- NPC появляется в офисе.

Не блокировать найм из-за низкого бюджета: механика банкротства ещё не реализована.

# 11. NPC на карте

После найма разработчик появляется в Open Space.

Каждый нанятый разработчик:

- регистрируется как отдельный NPC;
- имеет стабильный npc id;
- создаётся ровно один раз;
- восстанавливается после reload;
- использует общую навигацию;
- использует существующую state machine;
- использует claims;
- подключается к существующему автономному planner;
- может работать, пить кофе, ходить на встречу, сидеть и перемещаться.

Рекомендуемые ids:

```ts
"npc-kirill-morozov"
"npc-alina-belova"
```

Стартовые позиции должны быть разными, проходимыми и не внутри мебели.

Не назначать постоянный стол, если текущий planner выбирает рабочие места динамически.

## Ассеты

Используй только реальные ассеты, уже находящиеся в проекте.

Приоритет:

1. отдельные модели Кирилла и Алины;
2. существующие совместимые модели офисных персонажей, предназначенные для этих ролей.

Запрещено:

- кубы и примитивы;
- невидимые NPC;
- второй экземпляр Сони;
- скачивание новых ассетов;
- изменение общего формата анимаций.

Если подходящих ассетов нет:

1. останови реализацию после анализа;
2. перечисли отсутствующие файлы;
3. укажи ожидаемые пути и формат;
4. не создавай визуальную заглушку.

Отсутствие ассетов — блокер полного принятия Feature 03.

# 12. Задача «Сформировать команду»

После найма обоих разработчиков существующая задача `Сформировать команду` становится выполненной.

Требования:

- использовать существующее поле `done`;
- не создавать вторую задачу;
- найти стабильный id;
- если id нет — добавить минимально и мигрировать старое состояние;
- один найм не завершает задачу;
- повторный вызов идемпотентен;
- reload сохраняет `done`;
- reset возвращает `done: false`.

Не создавать полноценную механику выполнения произвольных задач. Это Feature 04.

# 13. Сохранение и миграция

Team-state сохраняется через существующий Zustand persist.

После reload восстанавливаются:

- hires;
- sprint/day найма;
- карточки `В команде`;
- динамические расходы;
- NPC на карте;
- выполненная задача формирования команды.

## Старое сохранение Feature 02

Если team-state отсутствует:

- создать `hires: []`;
- не сбрасывать игру;
- не нанимать автоматически;
- сохранить бюджет и журнал;
- не списывать зарплаты задним числом.

## Повреждённое сохранение

Безопасно удалить:

- неизвестные ids;
- дубликаты;
- некорректные sprint/day;
- запись Сони как hireable employee.

Не сбрасывать другие stores.

# 14. Reset

- очистить hires;
- убрать NPC Кирилла и Алины;
- вернуть задачу `Сформировать команду` в `done: false`;
- восстановить бюджет 2 500 000 ₽;
- оставить в журнале только стартовое финансирование;
- сбросить sprint-state;
- сохранить существующий пролог.

Не добавлять второй обработчик URL.

- мораль и усталость;
- задачи продукта;
- прогресс OfficeFlow;
- первый прототип;

# 20. Критерии готовности

Feature 03 принята, если:

- Соня отображается как текущий сотрудник;
- Кирилл и Алина нанимаются отдельно;
- нет альтернативных кандидатов;
- бюджет не списывается при найме;
- оба NPC появляются и не дублируются;
- первый спринт заблокирован до обоих наймов;
- задача формирования команды завершается;
- ежедневные расходы с обоими равны 37 000 ₽;
- полный спринт стоит 370 000 ₽;
- остаток после него — 2 130 000 ₽;
- сохранение, миграция и reset работают;
- сцена с монитором не запускается автоматически;
- задачи продукта, безопасник и DeepSeek не добавлены;
- тесты и production-сборка проходят.
